# Установка LORE на Linux

Самодостаточная установка LORE на чистую машину: своя ArcadeDB, бэкенд и веб-интерфейс. Внешних сервисов не
требует. Файлы (вложения, аватары) — своё S3 или без файлов. Вход через Keycloak, встройка Völva, Forgejo с
forgejo-mcp и мобильный монитор miniLORE — по выбору, каждый своим разделом ниже.

## Что скачать

Со страницы выпуска:

| файл | зачем | есть у выпуска |
|---|---|---|
| `lore-installer-<версия>.tar.gz` | `install.sh`, `docker-compose.install.yml`, `.env.example`, этот README и `lore-migrate.mjs` | всегда |
| `SHA256SUMS` | подписи вложений выпуска | всегда — проверьте перед установкой |
| `lore-src-<версия>.tar.gz` | исходники LORE для `--build-from-source` (сборка образов у себя) | обычно да |
| `lore-migrate-linux-x64` | то же, что `lore-migrate.mjs`, одним исполняемым файлом (125 МБ) | по просьбе: без него установщик запускает `.mjs` в контейнере с Node |
| `minilore-srv-<версия>.tar` | образ сервера miniLORE для `--minilore install` | по просьбе: ~150 МБ, нужен не всем |

Если нужного файла у выпуска нет — попросите того, кто его выпускал: вложения собираются по выбору, чтобы
страница выпуска не весила триста мегабайт у тех, кому хватает лёгкого архива.

Распакуйте архив и работайте из получившегося каталога — `install.sh`, compose и `.env.example` лежат рядом,
и установщик ищет их там же. Дополнительные вложения кладите туда же: **исходники в `src/`, образы в `images/`**
(каталоги создайте сами). Имена файлов менять не нужно: установщик ищет их по именам из этой таблицы.

```bash
tar -xzf lore-installer-<версия>.tar.gz && cd lore-installer-<версия>
sha256sum -c SHA256SUMS      # подписи
bash install.sh --dir /opt/lore --version v1.18.0
```

Без `--version` берётся версия пакета. Свой пароль базы вместо сгенерированного — переменной
`ARCADEDB_ROOT_PASSWORD`. Посмотреть план, ничего не меняя, — `--dry-run`: это стоит сделать первым запуском.

Если образы LORE уже есть в вашем реестре, сборку можно пропустить:

```bash
LORE_BACKEND_IMAGE=registry.example/lore-backend:v1.18.0 \
LORE_WEB_IMAGE=registry.example/lore-web:v1.18.0 \
bash install.sh --dir /opt/lore
```

## Требования

- Linux x86_64, 4 ГБ RAM и 10 ГБ диска (сборка образов — основная нагрузка).
- Docker Engine 24+ с плагином `docker compose` v2, пользователь в группе `docker`.
- `sha256sum` и `tar` (обычно уже есть), `git` — только если ставите по тегу из клона репозитория.
- Доступ к реестру образов: Docker Hub (ArcadeDB, Node, nginx, curl, debian) и, для готовых образов LORE,
  `ghcr.io`. **Доступа к Docker Hub нет — есть два пути, и они закрывают разные случаи:**
  - `LORE_IMAGE_REGISTRY=<ваше зеркало>/` в `.env` — работает для образов, которые пакет **запускает**
    (ArcadeDB, curl, debian, node). Префикс с косой чертой на конце, например `http://nexus:8083/`;
  - `registry-mirrors` в настройках самого Docker (`/etc/docker/daemon.json`, затем перезапуск) — нужен
    дополнительно, если **собираете образы из исходников**: базовые образы в `Dockerfile` переменной не
    перенаправить. Проверьте не кодом возврата, а делом: `docker pull eclipse-temurin:25-jre` должен скачать.
- Для сборки образов из исходников — выход к Maven Central и npm (или свои зеркала, см. «Настройка окружения»).
- Свободный порт веб-интерфейса (по умолчанию 4400); для Forgejo — ещё 3000 и 4430, если ставите его.
- Свой Keycloak — только если включаете вход (и обязательно, если ставите miniLORE: иначе телефон не войдёт).

## Как собирается схема при первой установке

Свежая база собирается из модели **установщиком**, а не бэкендом: шаг `lore-migrate init-empty` создаёт типы,
связи и справочники, после чего бэкенд стартует с `LORE_MIGRATE=false` — шаги миграций на такой базе не катятся,
они нужны только базам, которые старше модели.

Запускается это одним из двух способов, установщик выбирает сам:

- `lore-migrate.mjs` рядом с `install.sh` (он есть в архиве) — в одноразовом контейнере с Node;
- исполняемый файл, если вы его скачали, — путь к нему в `LORE_MIGRATE_BIN`.

Нет ни того, ни другого — установка остановится и скажет об этом словами. Флаг `LORE_BOOTSTRAP` не нужен.

## Настройка окружения

Все настройки установки — в одном файле `.env` в каталоге установки (права 600). Образец — `.env.example` пакета. Окно установщика собирает `.env` по вашему выбору кнопкой «Собрать .env», `install.sh` дописывает пароли и версию сам.

Что в нём по группам:

- **Версия и образы** — `LORE_VERSION`, `LORE_SRC` (каталог исходников, заполняет `install.sh`), `LORE_BACKEND_IMAGE` и `LORE_WEB_IMAGE` (готовые образы, тогда сборки нет).
- **База** — `ARCADEDB_VERSION`, `LORE_DB`, `ARCADEDB_ROOT_PASSWORD`.
- **Файлы** — `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` (см. «Хранилище файлов»).
- **Сеть** — `LORE_BIND` (по умолчанию `127.0.0.1`), `LORE_HTTP_PORT` (4400), `LORE_PUBLIC_URL` (https-адрес за reverse proxy).
- **Вход** — `LORE_AUTH_ENABLED`, `LORE_OIDC_ISSUER`, `LORE_OIDC_ORIGIN`, `LORE_OIDC_CLIENT_ID` (см. «Keycloak»).
- **Völva** — `LORE_VOLVA_ORIGIN`, `LORE_VOLVA_EMBED_SITE_URL`, `LORE_VOLVA_EMBED_ISSUER` (см. «Völva»).
- **Forgejo** — `COMPOSE_PROFILES`, `FORGEJO_*` (см. «Forgejo и forgejo-mcp»).
- **Локальная LLM** — `LORE_LLM_LOCAL_URL`, `LORE_LLM_LOCAL_MODEL`, `LORE_LLM_LOCAL_API_KEY` (см. «Локальная LLM»).

Пароли в образце — заглушки `CHANGE_ME`: оставленная заглушка значит «сгенерировать». Окно установщика пароли, токены и ключи в `.env` не передаёт — их генерирует `install.sh` или вписывает владелец. Какие секреты есть и как их сменить — раздел «Секреты рантайма».

После ручной правки `.env` — `docker compose up -d` в каталоге установки или повтор `install.sh` в тот же каталог.

## Собрать самому

Если готовые образы недоступны (нет доступа к ghcr, закрытая сеть), LORE собирается из исходников, которые лежат в пакете установщика. Это наш проект на том же коммите, из которого собран пакет.

- В каталоге версии пакета есть `src/lore-<версия>.tar.gz` и рядом `src/lore-<версия>.tar.gz.sha256`. Архив сделан `git archive`; файлов `.env*`, `*.secret`, `*.key` в нём нет.
- Положите каталог `src/` рядом с `install.sh` и запустите:

```bash
bash deploy/install/install.sh --dir /opt/lore --build-from-source
```

- `install.sh` сверяет sha256 архива. При несовпадении или без файла `.sha256` установка останавливается. Затем распаковывает архив в `<каталог установки>/src/<версия>/` и собирает образы бэкенда и веба на месте.
- Версия берётся из имени архива, `--version` с этим флагом не задаётся. Готовые образы (`LORE_BACKEND_IMAGE`, `LORE_WEB_IMAGE`) с этим флагом тоже не задаются — одно из двух.
- Свой архив вместо лежащего рядом — переменная `LORE_SRC_ARCHIVE=<путь к lore-<версия>.tar.gz>`.
- Сборке нужен доступ к Docker Hub, Maven Central и npm, как в разделе «Требования». Первая сборка — 10–20 минут.
- Прямой канал к Maven Central и Gradle Plugin Portal бывает закрыт или обрывается — тогда сборка бэкенда падает невнятным «Plugin [id: 'io.quarkus'] was not found». Свои зеркала задаются в `.env` установки (или в окружении): `LORE_MAVEN_MIRROR`, `LORE_PLUGIN_MIRROR`, `LORE_GRADLE_DIST_MIRROR` — например `http://<nexus>:8081/repository/maven-central-proxy/`, `http://<nexus>:8081/repository/gradle-plugins-proxy/`, `http://<nexus>:8081/repository/gradle-dist-proxy/`. Пусто — как раньше, напрямую.

Без флага всё как раньше: архив не трогается. В окне установщика это выбор на «Старте»: «готовые образы» или «собрать из исходников пакета».

## Обновление

Тот же запуск с новым тегом в тот же каталог:

```bash
bash deploy/install/install.sh --dir /opt/lore --version v1.18.0
```

Пароли из `.env` сохраняются. Перед накаткой новых шагов схемы бэкенд снимает бэкап базы в том `lore-db-backups`.

## Удаление

```bash
bash deploy/install/install.sh --dir /opt/lore --uninstall          # остановить, данные сохранить
bash deploy/install/install.sh --dir /opt/lore --uninstall --purge  # стереть всё, включая данные
```

## Что создаётся

- Каталог установки (`/opt/lore` по умолчанию, права 700):
  - `docker-compose.yml` — копия `docker-compose.install.yml`;
  - `.env` (права 600) — версия, пароли, порт;
  - `src/<тег>/` — исходники тега (или распакованный архив пакета при `--build-from-source`), из которых собраны образы.
- Контейнеры проекта compose `lore`: `arcadedb`, `lore-backend`, `lore-app-next`.
- Тома: `lore_lore-db` (база), `lore_lore-db-backups` (бэкапы перед миграциями). Файлы — в своём S3, на машине их нет.
- Наружу открыт только веб-интерфейс, по умолчанию на `127.0.0.1:4400`. База и бэкенд портов не публикуют.

## Если ставите дома, за роутером

Домашний роутер редко умеет «завернуть» запрос на ваш собственный внешний адрес обратно в дом (это называется
hairpin NAT). Из-за этого машины внутри дома, обращаясь к LORE по внешнему имени, уходят наружу и либо ждут
секунды, либо не доходят вовсе — а снаружи всё работает, и причина выглядит необъяснимой.

Поэтому внутри дома имена должны разрешаться во ВНУТРЕННИЙ адрес:

- либо своя запись в домашнем DNS (split-DNS): `lore.example.org → 10.0.0.20`;
- либо строка в `hosts` на каждой машине, которая ходит в LORE изнутри.

Проверять так: `getent hosts lore.example.org` изнутри дома должен показать внутренний адрес, а не внешний.
Если показывает внешний и запрос висит 1–4 секунды — это он и есть.

Та же оговорка про ICMP: `ping` может не отвечать там, где служба работает (его часто закрывают). Проверяйте
доступность запросом к самой службе, а не пингом.

## Проверка

Инсталлятор сам проверяет результат в конце. Повторить проверку:

```bash
bash deploy/install/install.sh --dir /opt/lore --verify
```

Проверяются здоровье бэкенда (`/q/health/ready`, `/lore/version`), непустой справочник `dictionary`, продуктовые слайсы `features`, `use_cases_of_feature`, `pains`, `gains`, `jobs`, `actors`, `asset_orphans` и поиск `/lore/search`. Запросы идут через веб-интерфейс, поэтому заодно проверяется его прокси к бэкенду.

## Безопасность

В этом профиле аутентификации нет (`LORE_AUTH_ENABLED=false`): любой, кто достучался до порта, читает и пишет данные. Поэтому порт по умолчанию слушает только localhost. Чтобы открыть LORE в сеть, поставьте перед ним reverse proxy с TLS и авторизацией и задайте `LORE_PUBLIC_URL`. Значение `--bind 0.0.0.0` выставляйте только осознанно.

## Keycloak — вход по выбору

По умолчанию входа нет (`LORE_AUTH_ENABLED=false`, см. «Безопасность»). Вход включается через Keycloak: свой или поставленный по ссылкам из окна установщика.

Наш Keycloak работает на встроенной H2 (dev-file). Для своей установки — внешняя БД (Postgres) и режим start, не start-dev.

Что нужно:

- Keycloak, до которого достают браузер и контейнер бэкенда. Нет своего — на «Старте» выберите «нет — скачать и настроить»: окно даст официальные ссылки и шаги запуска.
- Администратор Keycloak — только для новой установки. Окно спрашивает его логин и пароль, чтобы завести область. Пароль не пишется на диск и не сохраняется.
- Адрес веба LORE (`http(s)://хост[:порт]`, без пути): он становится адресом возврата клиента веба.

Сначала окно спрашивает, что у вас уже есть («Keycloak: что у вас уже есть»). Молча оно ничего не заводит:

- **ничего** — установщик заводит область и клиенты за вас;
- **своя область** — область не трогается, в ней заводятся клиенты;
- **LORE уже стоит** — доводка: недостающее дописывается, ничего не удаляется, секреты не перевыпускаются;
- **свои клиенты и секреты** — LORE ничего не заводит и секретов не пишет. Он только берёт токен по вашей паре «клиент + секрет из вашей переменной» и проверяет в нём `agent_scope` и `seer_roles`. В admin API не идёт ни одного запроса.

Имена клиентов по умолчанию — `lore-app` и `lore-mcp-<роль>[_<harness>]`. Своё имя впишите в поле «Свои имена клиентов» (`lore-mcp-full=acme-full`).

Как настроить:

1. В окне впишите «Адрес области Keycloak» (`https://<keycloak>/realms/<область>`) и «Адрес веба LORE», затем выберите, что уже есть.
2. «План области Keycloak» показывает запросы без записи: область, роли `superadmin`, `admin`, `viewer`, клиент веба `lore-app` и учётки MCP. Для доводки план читает область (нужен вход администратора), и каждая доводка видна отдельным шагом `fix-…`.
3. «Завести область» выполняет план. То, что уже есть, не трогается, поэтому повтор безопасен. Секреты выдаются только клиентам, заведённым в этом прогоне, ключами `LORE_MCP_CLIENT_SECRET_<РОЛЬ>[_<HARNESS>]`. Они уходят в Infisical, если запись настроена (ниже), иначе в файл `~/kc-clients-<область>.env` с правами 600. На экран секреты не выводятся.
4. «Собрать .env» включает вход: `LORE_AUTH_ENABLED=true`, `LORE_OIDC_ISSUER`, `LORE_OIDC_ORIGIN`, `LORE_OIDC_CLIENT_ID=lore-app`. Веб берёт их при запуске контейнера, в образ они не впекаются: после смены адреса или клиента достаточно `docker compose up -d`. Включение и выключение входа (`LORE_AUTH_ENABLED`) бэкенд фиксирует при сборке (`quarkus.oidc.enabled`), поэтому смена этого флага — повтор `install.sh`.
5. Первому владельцу выдайте в Keycloak роль `superadmin`.

Настройки клиентов совпадают с ранбуком LORE RUNBOOK-CORE-KC-INFISICAL-LOREHOST: так заведены 9 клиентов прод-KC.

- **Клиент веба `lore-app`.** Публичный, PKCE S256. Адрес возврата `<веб>/*`, адрес после выхода тот же («+»), web origins — адрес веба.
- **Учётки MCP.** Роли идут по порядку модели (`shared/model/lore-model.json`, раздел `agent_profiles`): full > architect > pm > (product-analyst | analyst | developer | marketer) > tester.
  - Для Claude Code заводятся все роли: `lore-mcp-<роль>`.
  - У другого harness заводится главная роль `lore-mcp-<главная>_<harness>` (у kimi это `lore-mcp-full_kimi`) и младшие из поля «Младшие роли для harness». Роль выше главной не заводится.
  - У каждой учётки: Client authentication ON, Service accounts ON, Standard flow и Direct access OFF. Мапперы `agent_scope` (User Client Role) и `seer_roles` (User Realm Role). Клиентская роль `agent-<роль>` своего клиента выдана его сервисной учётке.
  - Realm-роль `admin` есть только у главной `full`.
  - Без `agent_scope` учётка только читает, а на запись получает 403.
- **Смена секрета без простоя.** Нужны оба условия: флаг Keycloak `--features=…,client-secret-rotation` и клиентская политика `secret-rotation` в области. Без них при смене секрета старый перестаёт работать сразу.

### Подключение harness: какой секрет брать

Секрет учётки лежит под ключом `LORE_MCP_CLIENT_SECRET_<РОЛЬ>[_<HARNESS>]`, заглавными буквами, «-» заменяется на «_». Примеры: `LORE_MCP_CLIENT_SECRET_FULL` для Claude Code, `LORE_MCP_CLIENT_SECRET_FULL_KIMI`, `LORE_MCP_CLIENT_SECRET_TESTER`. Переменная `LORE_MCP_SECRET_VAR` говорит подключению, из какого ключа брать секрет. У подагента младшей роли — своя учётка и свой ключ.

Строка MCP для Claude Code (главная учётка `lore-mcp-full`):

```json
"aida-lore": { "type": "stdio", "command": "node", "args": ["<путь>/mcp-server/dist/index.js"],
  "env": { "LORE_BACKEND_URL": "http://<хост>:9100", "LORE_OIDC_ISSUER": "https://<keycloak>/realms/<область>",
           "LORE_MCP_CLIENT_ID": "lore-mcp-full", "LORE_MCP_SECRET_VAR": "LORE_MCP_CLIENT_SECRET_FULL",
           "LORE_HARNESS": "claude-code", "LORE_MACHINE_ID": "<машина>" } }
```

Окно установщика собирает эту строку само: кнопка «Показать строку MCP» в разделе «Подключение агента на этой машине».

Для другого harness, например Kimi Code (главная `lore-mcp-full_kimi`), меняются только имя клиента и ключ: `"LORE_MCP_CLIENT_ID": "lore-mcp-full_kimi"`, `"LORE_MCP_SECRET_VAR": "LORE_MCP_CLIENT_SECRET_FULL_KIMI"`, `"LORE_HARNESS": "kimi-code"`.

### Infisical — по выбору

Секреты учёток MCP можно класть в отдельный проект Infisical, например `lore-mcp-secrets` с окружением `prod`. Машинной учётке LORE нужна в нём роль member, и только в нём: свои роли проекта Infisical бесплатно не даёт, поэтому узкий доступ делается отдельным проектом. Запись включается, когда заданы `LORE_MCP_SECRETS_INFISICAL_URL`, `LORE_MCP_SECRETS_INFISICAL_PROJECT_ID`, `LORE_MCP_SECRETS_INFISICAL_CLIENT_ID` и `LORE_MCP_SECRETS_INFISICAL_CLIENT_SECRET`. Необязательные: `LORE_MCP_SECRETS_INFISICAL_ENVIRONMENT` (по умолчанию `prod`) и `LORE_MCP_SECRETS_INFISICAL_PATH` (по умолчанию `/`).

- **Кто пишет.** Окно установщика (переменные выше) и, с 1.18.2, бэкенд LORE — после выпуска учётки и после смены секрета в админке (Агенты → «Учётки harness»). У бэкенда свои имена: `LORE_MCP_SECRETS_URL`, `LORE_MCP_SECRETS_PROJECT_ID`, `LORE_MCP_SECRETS_ENVIRONMENT` (по умолчанию `prod`), `LORE_MCP_SECRETS_PATH` (по умолчанию `/`); учётку записи `LORE_MCP_SECRETS_CLIENT_ID` и `LORE_MCP_SECRETS_CLIENT_SECRET` он берёт сначала из своего хранилища секретов (Infisical `lore-secrets`), а из окружения — запасным путём. Не задано — админка говорит «запись в Infisical не настроена» и показывает секрет один раз; сбой записи — громкая ошибка, секрет всё равно показан один раз.
- **stdio-подключение.** MCP читает секрет из переменной, имя которой задано `LORE_MCP_SECRET_VAR` (по умолчанию `LORE_MCP_CLIENT_SECRET`); переменной нет — ошибка называет её имя, значение не печатается.
- **Не настроено.** Секрет показывается один раз, как раньше.
- **Сбой записи.** Секрет всё равно показывается один раз, а ошибка выводится громко.

## Подключить агента к MCP

MCP-сервер LORE ставится вместе со стеком (сервис `lore-mcp`). Своего порта у него нет: агент ходит на `https://<хост>/mcp` через nginx веба — тот же адрес и порт, что у веба LORE (`LORE_PUBLIC_URL`). Проверка без входа — `https://<хост>/mcp/health`. После установки `install.sh` проверяет оба адреса: `/mcp/health` отвечает 200, `POST /mcp` без входа — 401 (или 405). 502 значит, что nginx не достал `lore-mcp`, 404 — что `/mcp` не проксируется.

- **Вход выключен** (`LORE_AUTH_ENABLED=false`, по умолчанию). `/mcp` всё равно ждёт заголовок `Authorization: Bearer <что-нибудь>`, но бэкенд без входа токен не проверяет. Пускайте агентов только с этой машины или через свой прокси с авторизацией: MCP пишет в базу так же, как веб (см. «Безопасность»).
- **Вход через Keycloak.** У каждого агента своя учётка `lore-mcp-<роль>[_<harness>]`, её заводит окно установщика (раздел «Keycloak» выше). Секрет учётки лежит под ключом `LORE_MCP_CLIENT_SECRET_<РОЛЬ>[_<HARNESS>]`, например `LORE_MCP_CLIENT_SECRET_FULL` для Claude Code или `LORE_MCP_CLIENT_SECRET_FULL_OPENCODE`. Переменная `LORE_MCP_SECRET_VAR` называет ключ, из которого подключение берёт секрет; без неё берётся `LORE_MCP_CLIENT_SECRET`. Значение секрета держите в окружении машины агента или в Infisical, в файлы настроек его не вписывайте. Подагенту младшей роли — своя учётка и свой ключ.
- **Без MCP.** Если образа `lore-mcp` нет (своего `LORE_MCP_IMAGE` нет, а в реестре выпуска его не оказалось), установка не падает. Она громко пишет «MCP не будет запущен», а проверка показывает строку «НЕТ lore-mcp». Выход — свой `LORE_MCP_IMAGE` или повтор с `--build`.

### Claude Code (http + headersHelper)

Токен client_credentials живёт минуты, поэтому его выдаёт помощник `mcp-server/scripts/lore-mcp-headers.mjs` из исходников LORE. Claude Code запускает его при подключении и после 401. В окружении Claude Code нужны `LORE_OIDC_ISSUER` (`https://<keycloak>/realms/<область>`), `LORE_MCP_CLIENT_ID` (`lore-mcp-full`), `LORE_MCP_SECRET_VAR` (`LORE_MCP_CLIENT_SECRET_FULL`) и сам ключ `LORE_MCP_CLIENT_SECRET_FULL`. По желанию — `LORE_MCP_PROFILE` (по умолчанию `full`), `LORE_HARNESS`, `LORE_MACHINE_ID`.

```json
{
  "mcpServers": {
    "aida-lore": {
      "type": "http",
      "url": "https://<хост>/mcp",
      "headersHelper": "node <путь>/mcp-server/scripts/lore-mcp-headers.mjs"
    }
  }
}
```

### OpenCode

Удалённо (`remote`). OpenCode не умеет обновлять токен, поэтому он шлёт пару «клиент + секрет», а токен по ней берёт сам сервер MCP. Для этого у сервиса `lore-mcp` должен быть задан `LORE_OIDC_ISSUER` в `.env` установки, иначе вход парой отвечает 503. `"oauth": false` обязателен: без него OpenCode на 401 уходит искать OAuth и отправляет заголовки с секретом на чужие пути. Адрес — только `https://`, потому что секрет едет в каждом запросе.

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "aida-lore": {
      "type": "remote",
      "url": "https://<хост>/mcp",
      "enabled": true,
      "oauth": false,
      "headers": {
        "X-Lore-Client-Id": "lore-mcp-full_opencode",
        "X-Lore-Client-Secret": "{env:LORE_MCP_CLIENT_SECRET_FULL_OPENCODE}",
        "X-Lore-Mcp-Profile": "full",
        "X-Lore-Harness": "opencode",
        "X-Lore-Machine": "{env:LORE_MACHINE_ID}"
      }
    }
  }
}
```

Локально (`local`). MCP запускается на машине агента из исходников (`cd mcp-server && npm ci && npm run build`) и ходит в LORE через тот же nginx: `LORE_BACKEND_URL` — адрес веба, без `/mcp`. Токен процесс берёт сам и обновляет его.

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "aida-lore": {
      "type": "local",
      "command": ["node", "<путь>/mcp-server/dist/index.js"],
      "enabled": true,
      "environment": {
        "LORE_BACKEND_URL": "https://<хост>",
        "LORE_OIDC_ISSUER": "https://<keycloak>/realms/<область>",
        "LORE_MCP_CLIENT_ID": "lore-mcp-full_opencode",
        "LORE_MCP_CLIENT_SECRET": "{env:LORE_MCP_CLIENT_SECRET_FULL_OPENCODE}",
        "LORE_HARNESS": "opencode"
      }
    }
  }
}
```

Файл настроек OpenCode — `opencode.json` в проекте или в `~/.config/opencode/`.

## Völva — встроенные графики

По выбору. Völva ставится своей поставкой, установщик настраивает только связь: LORE подписывает встройку ключом ES256, Völva проверяет подпись.

Как настроить:

1. На «Старте» отметьте Völva и впишите «Адрес Völva» и «Адрес веба LORE».
2. «Ключи Völva» создаёт пару ES256 и пишет её в файл `volva-embed.env` (права 600). На экране — только открытый ключ.
3. Перенесите обе строки (`LORE_VOLVA_EMBED_ES256_PRIVATE_KEY`, `LORE_VOLVA_EMBED_ES256_PUBLIC_KEY`) в `.env` установки или в своё хранилище и выполните `docker compose up -d`.
4. «Собрать .env» кладёт адреса: `LORE_VOLVA_ORIGIN`, `LORE_VOLVA_EMBED_SITE_URL`, `LORE_VOLVA_EMBED_ISSUER` (издатель — origin веба LORE).
5. На стороне Völva впишите тот же издатель в `MB_EMBEDDING_JWT_ISSUERS`. Ключи Völva берёт с `<адрес веба LORE>/lore/embed/jwks`.

Без адреса веба LORE издатель не задан, и подпись остаётся временной. Проверка — «Проверить связь» в окне: ключ установки должен быть опубликован в `/lore/embed/jwks`.

## Forgejo и forgejo-mcp — по выбору

Три варианта, по умолчанию — без Forgejo, как раньше:

```bash
bash deploy/install/install.sh --version v1.18.0 --forgejo install                                   # поставить Forgejo 17.0.2
bash deploy/install/install.sh --version v1.18.0 --forgejo own --forgejo-url https://git.example.org  # свой Forgejo
bash deploy/install/install.sh --version v1.18.0 --forgejo none                                      # без Forgejo
```

- **install** — пакет поднимает Forgejo 17.0.2 (образ `codeberg.org/forgejo/forgejo`) и forgejo-mcp. Профили compose `forgejo` и `forgejo-mcp`, веб Forgejo — на `127.0.0.1:3000`. Администратора Forgejo вы заводите сами в его первом окне.
- **own** — Forgejo не ставится. Адрес вашего Forgejo уходит в forgejo-mcp (`FORGEJO_URL`), профиль compose — только `forgejo-mcp`.
- **none** — профили Forgejo снимаются, мост LORE отвечает 503, как без Forgejo.

В вариантах install и own в пакет входит **forgejo-mcp**: репозиторий `AIDA/forgejo-mcp`, версия 0.1.7 с нашими
доработками, тег `v0.1.7-aida.1` (форк `@ric_/forgejo-mcp` с инструментами Actions/CI). Исходники прибиты к
коммиту `e7d57dee`. В нём, среди прочего, исправлен запрос списков к Forgejo 17: без явного указания страницы
ограничение на число записей игнорировалось, и «дай шесть прогонов» возвращало всё подряд.

Образ forgejo-mcp ни в какой реестр не публикуется. Пакет установщика везёт его двумя способами, оба со сверкой sha256: архивом образа `images/forgejo-mcp-e7d57dee.tar` и исходником того же коммита `src/forgejo-mcp-e7d57dee.tar.gz` (рядом лицензия MIT — `src/forgejo-mcp-e7d57dee.LICENSE`). Положите каталоги `images/` и `src/` рядом с `install.sh`. Сети к чьему-либо git установке не нужно. Порядок выбора:

1. `FORGEJO_MCP_IMAGE` — ваш готовый образ, перекрывает всё остальное.
2. `FORGEJO_MCP_SRC` — ваши исходники (каталог или git-адрес#коммит), сборка.
3. Архив образа из `images/` — `docker load`, только если sha256 сходится. `--forgejo-mcp-build` этот шаг пропускает.
4. Исходник из `src/` — распаковка в каталог установки и сборка, только если sha256 сходится.

Если нет ни одного источника, инсталлятор в терминале спрашивает: git-адрес исходников, готовый образ или «без forgejo-mcp». Без терминала он отказывается и называет варианты — молча ничего не подставляет. Агенты подключаются по HTTP: `http://127.0.0.1:4430/mcp` с заголовком `Authorization: Bearer ${FORGEJO_MCP_API_KEY}`.

После установки:

1. Создайте в Forgejo два токена (Настройки → Приложения, права на репозитории): один для моста LORE, другой для forgejo-mcp.
2. Впишите их в `.env` установки как `FORGEJO_API_TOKEN` и `FORGEJO_MCP_TOKEN`.
3. Повторите `install.sh` в тот же каталог. Это обновление: пароли сохраняются, поднимается forgejo-mcp.

Пока `FORGEJO_MCP_TOKEN` пуст, forgejo-mcp не запускается, и инсталлятор пишет об этом предупреждение.

Проект в LORE регистрируется с адресом репозитория: `<адрес Forgejo>/<организация>/<репозиторий>`. Из этого адреса мост берёт организацию и репозиторий. При своей установке Forgejo используйте `http://localhost:3000/...`: бэкенд из контейнера ходит на этот адрес через `forgejo:3000` (`FORGEJO_BASE_OVERRIDE`).

## miniLORE — мобильный монитор сессий (по выбору)

`install.sh --minilore install` поднимает **сервер miniLORE** в той же установке. По умолчанию он не ставится.

**Что входит в этой версии и чего нет.** Входит только сервер. Установщик шлюза (Windows и Linux) и приложение
для телефона (APK) выйдут следующей версией: сборочная труба приложения сейчас не зелёная, а раздавать файл,
который не собрала труба, нельзя — вы не сможете его воспроизвести и проверить.

**База — ваша же ArcadeDB.** Базы `minilore` и `minilore_archive` заводит **установщик**, чужих баз не трогает.
Раньше здесь было написано, что их заводит сам сервер; на версии 0.4.19 это неверно — он сразу катит свои миграции
и падает с `Database not found`, уходя в бесконечный перезапуск (поймано живым прогоном 22.11.2026).
Порт наружу не публикуется: снаружи miniLORE доступен только через ваш прокси, если вы его заводите.

**Образ сервера** едет в пакете архивом `images/minilore-srv-0.4.19.tar` и грузится `docker load` при совпадении
подписи `sha256` — как и образ forgejo-mcp. Из сети он не тянется: имя образа в пакете локальное
(`minilore-srv:0.4.19`), адресов наших реестров в пакете нет. Свой образ — переменной `MINILORE_IMAGE`.

**Два значения обязательны — без них установка не начнётся.** Так сделано по живому прогону на чужой машине
22.11.2026: сервер miniLORE без них не запускается вовсе (`Failed to load config value … minilore.app.client-id`)
и уходит в бесконечный перезапуск. Раньше установщик ограничивался предупреждением — установка «проходила», а
контейнер крутился в рестарте, и вы узнавали об этом сами, разбирая журналы.

| ключ | ключ запуска | что это |
|---|---|---|
| `MINILORE_APP_CLIENT_ID` | `--minilore-client-id` | ваш клиент мобильного приложения в Keycloak |
| `MINILORE_OWNER` | `--minilore-owner` | ваш логин — чьи это записи |

Значения берутся из ключей запуска, из окружения с теми же именами или из уже лежащего `.env` — в этом порядке.

У клиента приложения обязаны быть: redirect `pro.seidrstudio.minilore://auth/callback` (схема вшита в приложение
и не меняется), public client, PKCE S256, маппер audience `minilore-srv`.

Умолчаний у этих двух значений нет намеренно: имя клиента и имя владельца у разработчика свои, и тихая
подстановка увела бы вашу установку в чужой Keycloak, под чужое имя.

**Проверка после установки.** Порт miniLORE наружу не публикуется, поэтому проверять его нужно изнутри
установки, из каталога, куда вы ставили:

```bash
docker compose ps minilore-srv                                            # running, а не restarting
docker compose exec minilore-srv wget -qO- http://127.0.0.1:8080/config   # настройки сервера
```

В ответе смотрите на два поля: `kcClientId` — ваш клиент приложения (не пустой), `kcIssuer` — адрес вашего
Keycloak. `kcIssuer: null` значит, что вход LORE не настроен: сервер работает, но телефон войти не сможет.


### Шлюз miniLORE — выпуск link-v0.3.80

**Что это.** Программа на вашей машине (не в этом стеке), которая показывает телефону живые сессии агентов —
Claude Code, Qwen, OpenCode, Kimi — и позволяет им отвечать, передавать картинки и файлы и закрывать их с телефона. Сервер miniLORE из этого
пакета без шлюза работает, но показывать ему будет нечего: сессии видит именно шлюз.

**Честный статус — прочитайте до установки.** Это настоящий выпуск: тег `link-v0.3.80`, байты собраны трубой, а
не руками на чьей-то машине. Но одно сказать обязаны: **на Linux он живьём не проверялся** — проверен на
Windows. Файлы под Linux собраны той же трубой из того же кода, однако запуска на Linux пока никто не видел.
Нужна версия, обкатанная дольше, — возьмите предыдущий выпуск шлюза.

Мы говорим это прямо, потому что иначе вы узнали бы сами и в худший момент.

**Файлы** — вложения выпуска, рядом с этим пакетом. Размеры и подписи берите из `SHA256SUMS` выпуска и
проверяйте ПЕРЕД установкой: это единственный способ убедиться, что вам достались те самые байты, которые
собрала труба.

| файл | для чего | размер |
|---|---|---|
| `miniLORE-link-setup-0.3.80.exe` | Windows, обычный установщик | 21,9 МБ |
| `minilore-link_0.3.80_amd64.deb` | Debian и Ubuntu | 46,4 МБ |
| `minilore-link-linux-0.3.80.tar.gz` | другие Linux; нужен системный Node 22 и новее | 3,6 МБ |

**Как поставить.**

```bash
# Windows (тихая установка)
miniLORE-link-setup-0.3.80.exe /S

# Debian/Ubuntu
sudo dpkg -i minilore-link_0.3.80_amd64.deb

# другой Linux
tar -xzf minilore-link-linux-0.3.80.tar.gz && cd minilore-link-0.3.80 && ./install.sh
```

**Обязательная настройка.** Шлюзу нужен файл `~/.minilore/config.toml`: адрес вашего сервера miniLORE, код этой
машины и данные входа. Без него шлюз запустится, но соединиться ему будет не с чем. Формат тот же, что у 0.3.62.

**Как проверить.** После установки и настройки откройте телефон: машина должна появиться в списке, а её сессии —
показываться живыми. Если машина видна, а сессий нет — смотрите журнал шлюза: чаще всего дело в коде машины,
который не совпадает с заведённым в LORE.

**Чего в пакете нет.** Мобильного приложения (APK): его выпуск собрался без файла приложения — труба сборки у
разработчика красная. Как починят и соберут — приложение приедет следующей версией пакета.

## Локальная LLM: векторный индекс и гейты качества

По выбору. Без модели LORE работает полностью, как раньше. Платные провайдеры (Anthropic и другие) не подключены — только своя модель на своей машине.

### Что даёт каждая часть

| часть | что даёт | в этой версии |
|---|---|---|
| **Гейты качества (QG)** | рутина считает метрики сама, затем модель пишет к ним короткое суждение. На числа модель не влияет: метрики готовы до её вызова | подключение есть. Но ни одна рутина суждения ещё не просит — переменные готовят место |
| **Векторный индекс** | поиск по смыслу, а не по словам: найти похожие задачи и решения до заведения новых, затем соседей по графу (ADR-LORE-057, D-2026-GRAPH-SEARCH-VECTOR-PROBE) | **будет в версии после 1.18.** Кода индекса, эмбеддингов и их настроек в этой версии нет, вписывать нечего |

### Какие модели проверены

- **Эмбеддинги — Qwen3-Embedding, размерность 1024** (проба 19.11.2026). Сервер — `llama-server`, `/v1/embeddings`, только плотный вектор. Индекс — `LSM_VECTOR` в ArcadeDB 26.11.1, создан и опрошен на копии базы. Сходство пар-дублей 0,55–0,71, несвязанных пар — 0,33–0,44. Это проба, а не настройка: в установку эмбеддинги пока не подключаются.
- **Чат для суждений QG — любая модель за OpenAI-совместимым API.** Первый живой прогон (27.08.2026) — Qwen3. У рассуждающих моделей потолок токенов может уйти на размышление, и тогда ответ придёт пустым (`finish_reason=length`). LORE пишет это как «не измерено» с причиной, а не как пустой ответ.

### Как поднять сервер модели

LORE ходит в модель на диалекте OpenAI: `POST <адрес>/v1/chat/completions`. Подходит любой раннер с этим API. Пример с Ollama на той же машине, что и LORE:

```bash
# Ollama: слушать не только localhost, чтобы контейнер бэкенда достучался
OLLAMA_HOST=0.0.0.0:11434 ollama serve &
ollama pull qwen3:4b
curl -s http://127.0.0.1:11434/v1/models     # модель в списке
```

OpenAI-совместимый `llama-server` из llama.cpp — так стоит модель на нашей машине:

```bash
llama-server -m <модель>.gguf --host 0.0.0.0 --port 8086 --alias qwen3-4b
# вектора для будущего индекса — отдельный процесс:
# llama-server -m <Qwen3-Embedding>.gguf --embedding --host 0.0.0.0 --port 8088
```

vLLM (`vllm serve <модель> --port 8000`) и LM Studio (сервер на `:1234`) подключаются так же: нужен адрес и имя модели.

### Какие переменные вписать

В `.env` установки (образец — `.env.example`, окно установщика заполняет их в шаге «LLM»):

| переменная | что | пример |
|---|---|---|
| `LORE_LLM_LOCAL_URL` | адрес сервера модели **без** `/v1`. Модель на той же машине — `host.docker.internal`, пакет пробрасывает это имя в контейнер бэкенда | `http://host.docker.internal:11434`, `http://llm.example.org:8086` |
| `LORE_LLM_LOCAL_MODEL` | имя модели, как его отдаёт `/v1/models`. Пусто — провайдер отвечает «локальная модель не задана» | `qwen3:4b`, `qwen3-4b` |
| `LORE_LLM_LOCAL_API_KEY` | ключ, только если раннер его требует (`--api-key`). Уходит заголовком `Authorization: Bearer` | пусто |

После правки — `docker compose up -d lore-backend` в каталоге установки.

Что ещё нужно гейтам качества. Это настройки рутины, а не переменные пакета (`backend/src/main/resources/application.properties`, `QgLlmSettings`):

- **Цена.** `lore.llm.price.local.*=0` — уже задана, локальная модель бесплатна.
- **Потолок рутины.** `lore.qg.routines.<имя>.max-tokens` или `max-usd`. Умолчания нет намеренно: без потолка модель не вызывается, флаг прогона `budget: budget_unset`. Когда рутина получит суждение, потолок задаётся переменной окружения бэкенда по правилу MicroProfile Config. Например, `LORE_QG_ROUTINES_QG_SUPERVISOR_MAX_TOKENS=20000`.
- **Модель рутины.** `lore.qg.routines.<имя>.model`. Пусто — `local`.

### Как проверить, что подключилось

1. Сервер модели виден из контейнера бэкенда:
   ```bash
   docker compose exec lore-backend curl -fsS "$LORE_LLM_LOCAL_URL/v1/models"
   ```
   Должен прийти JSON со списком моделей, и `LORE_LLM_LOCAL_MODEL` в нём есть. Ошибка соединения — модель слушает только `127.0.0.1` (Ollama: `OLLAMA_HOST=0.0.0.0`) или закрыт порт.
2. Модель отвечает тем запросом, которым её зовёт LORE:
   ```bash
   docker compose exec lore-backend curl -fsS "$LORE_LLM_LOCAL_URL/v1/chat/completions" \
     -H 'Content-Type: application/json' \
     -d "{\"model\":\"$LORE_LLM_LOCAL_MODEL\",\"messages\":[{\"role\":\"user\",\"content\":\"ok?\"}],\"max_tokens\":64}"
   ```
   В ответе `choices[0].message.content` не пустой. Если пустой, а `finish_reason` = `length` — поднимите `max_tokens`.
3. В самом LORE: в прогоне рутины QG с суждением поле `model` заполнено, а строка суждения — с числом токенов. Отдельной ручки «проверить модель» у бэкенда нет.

### Что будет без модели

- **Поиск «похожих»** (`search_similar`, `/lore/search/similar`) работает на полнотексте ArcadeDB: совпадение слов, а не смысла. Так же работает и с моделью, пока нет векторного индекса.
- **Рутины QG** считают и пишут метрики как обычно. Суждения нет:
  - модель не задана или недоступна — строка суждения «не измерено», причина `source_unreachable`;
  - нет потолка или цены — `budget_exhausted` с флагом `budget_unset` или `price_unknown`;
  - у рутины без аналитика (в этой версии — у всех) модель не вызывается вовсе.

## Рекомендации: что стоит доделать после установки

Пакет ставит рабочую LORE, но «рабочая» и «готовая к жизни» — не одно и то же. Ниже то, чего пакет НЕ делает за
вас, и что обычно нужно. Решать вам: каждый пункт отдельный, без него установка работает — но хуже, и ровно в
названных местах. Форма одинаковая: что это, что будет без этого, как сделать, как проверить.

Пункты собраны по итогам нашей собственной эксплуатации (CICDGitHub, 22.11.2026) — это не теория, а то, на чём
спотыкались мы сами.

### 1. HTTPS-прокси перед LORE

**Что это.** Обратный прокси с настоящим сертификатом перед веб-интерфейсом. В этом пакете веб и MCP живут на
одном порте (`4400`): MCP доступен путём `/mcp` через тот же nginx, своего порта у него нет. Сервер miniLORE
порт наружу не публикует вовсе — до него прокси должен дотянуться в сети стека.

**Что будет без этого.** LORE откроется только по `http://адрес:4400` в локальной сети. MCP-клиенты, которым
нужен https (агенты в редакторах, удалённые подключения), не подключатся. Телефон с приложением miniLORE не
войдёт: вход через Keycloak и обращения к API требуют https. Браузер будет ругаться на небезопасное соединение.

**Как сделать — Caddy** (сертификат получает сам; нужны открытые 80 и 443 и DNS-имя на эту машину):

```caddy
# /etc/caddy/Caddyfile
lore.example.org {
    reverse_proxy 127.0.0.1:4400        # и веб, и /mcp — это один порт пакета
}

# только при профиле miniLORE: его порт наружу не опубликован,
# поэтому Caddy должен быть в сети стека (--network <проект>_default)
minilore.example.org {
    reverse_proxy minilore-srv:8080
}
```

**Как сделать — Traefik** (файловый провайдер; `certResolver: le` настраивается в статической конфигурации):

```yaml
# dynamic/lore.yml
http:
  routers:
    lore-web:
      rule: "Host(`lore.example.org`)"
      service: lore-web
      tls: { certResolver: le }
    minilore:                                  # только при профиле miniLORE
      rule: "Host(`minilore.example.org`)"
      service: minilore
      tls: { certResolver: le }
  services:
    lore-web: { loadBalancer: { servers: [ { url: "http://127.0.0.1:4400" } ] } }
    minilore: { loadBalancer: { servers: [ { url: "http://minilore-srv:8080" } ] } }
```

**Как проверить.**

```bash
curl -sS -o /dev/null -w '%{http_code} %{ssl_verify_result}\n' https://lore.example.org/
# ожидаемо: 200 0   (ноль во втором поле — сертификат проверен)
curl -sS -o /dev/null -w '%{http_code}\n' https://lore.example.org/mcp
# ожидаемо: 401 или 405 — MCP жив и просит ключ. НЕ 404 и НЕ 502
```

### 2. Внутреннее имя — на внутренний адрес (если ставите дома)

Причина и объяснение — в разделе «Если ставите дома, за роутером» выше. Здесь готовые куски.

**Машина с systemd-resolved** (ваш DNS спрашивается только про ваш домен):

```bash
sudo mkdir -p /etc/systemd/resolved.conf.d
sudo tee /etc/systemd/resolved.conf.d/lore-split.conf <<'CONF'
[Resolve]
DNS=10.0.0.10          # локальный DNS, который знает внутренние адреса
Domains=~example.org      # тильда означает «только для этого домена»
CONF
sudo systemctl restart systemd-resolved
```

Своего DNS нет — строка в `/etc/hosts` на каждой машине:
`10.0.0.20  lore.example.org minilore.example.org`.

**dnsmasq на роутере или сервере** (работает сразу у всех, включая телефоны):

```conf
# /etc/dnsmasq.d/lore.conf
address=/lore.example.org/10.0.0.20
address=/minilore.example.org/10.0.0.20
```

…и раздавать этот dnsmasq как DNS в DHCP роутера; вторым — любой публичный, на случай его падения.

**Как проверить.**

```bash
getent ahosts lore.example.org | head -1
# ожидаемо: адрес вашей домашней сети, а не внешний адрес роутера
curl -sS -o /dev/null -w 'connect=%{time_connect} total=%{time_total}\n' https://lore.example.org/
# ожидаемо: connect меньше 0,05 с. Секунды — значит запрос уходит через внешний адрес
```

Цифры не выдуманы: у нас 22.11.2026 через внешний адрес соединение занимало 1,0–4,2 секунды и дало 13 таймаутов
за десять минут; через внутренний — 13–21 миллисекунду.

### 3. Бэкап базы и проверка, что он восстанавливается

**Что это.** Регулярный снимок баз ArcadeDB встроенной командой, счёт записей на момент снимка — и отдельная
проверка, что снимок действительно разворачивается.

**Что будет без этого.** Весь граф LORE — задачи, решения, история — лежит в одной базе. Сбой диска, неудачное
обновление или ошибочная массовая правка, и возвращать нечего. Бэкап без проверки восстановления — это надежда,
а не бэкап: архив может оказаться пустым или битым ровно тогда, когда понадобится.

**Важно для этого пакета:** порт базы наружу не публикуется. Поэтому запросы к ней идут одноразовым контейнером
в сети стека — так же, как это делает сам установщик.

```bash
#!/bin/bash
# /opt/lore/backup.sh — например, в cron: 30 2 * * * /opt/lore/backup.sh
set -uo pipefail
STACK=/opt/lore                      # каталог установки (--dir)
OUT=/opt/lore-backups/$(date +%F); mkdir -p "$OUT"; chmod 700 "$OUT"
PROJ=$(grep -m1 '^COMPOSE_PROJECT_NAME=' "$STACK/.env" | cut -d= -f2-); PROJ=${PROJ:-lore}
PASS=$(grep -m1 '^ARCADEDB_ROOT_PASSWORD=' "$STACK/.env" | cut -d= -f2-)
ARC=$(docker compose -f "$STACK/docker-compose.yml" ps -q arcadedb)
# пароль уходит в контейнер файлом настроек curl, а не аргументом: аргументы видны в списке процессов
ac() { printf 'user = "root:%s"\n' "$PASS" | docker run -i --rm --network "${PROJ}_default" \
        curlimages/curl:latest -K - -sS -m 900 -H 'Content-Type: application/json' "$@"; }
A=http://arcadedb:2480
: > "$OUT/MANIFEST"                  # что именно забрали этой ночью — им же и проверять
for db in $(ac "$A/api/v1/databases" | sed 's/.*"result":\[//;s/\].*//;s/"//g;s/,/ /g'); do
  # ответ команды содержит ИМЯ созданного файла — берём его, а не угадываем по маске
  R=$(ac -d '{"language":"sql","command":"BACKUP DATABASE"}' "$A/api/v1/command/$db")
  F=$(printf '%s' "$R" | sed -n 's/.*"backupFile":"\([^"]*\)".*/\1/p')
  if [ -z "$F" ]; then echo "ОШИБКА: BACKUP $db — $R"; continue; fi
  # архив лежит в подкаталоге по имени базы: backups/<база>/<файл>
  docker cp "$ARC:/home/arcadedb/backups/$db/$F" "$OUT/" || { echo "ОШИБКА: не забрали $F"; continue; }
  # и сразу убираем его из тома: том с бэкапами иначе растёт без предела
  docker run --rm --volumes-from "$ARC" alpine:3 rm -f "/home/arcadedb/backups/$db/$F"
  printf '%s %s\n' "$db" "$F" >> "$OUT/MANIFEST"
  ac -d '{"language":"sql","command":"select name, records from schema:types order by name"}' \
     "$A/api/v1/command/$db" > "$OUT/counts-$db.json"
done
( cd "$OUT" && sha256sum ./* > SHA256SUMS )
find /opt/lore-backups -maxdepth 1 -type d -mtime +7 -exec rm -rf {} +    # хранить неделю
```

Две вещи в этом скрипте сделаны именно так не случайно, и обе проверены на живой базе 22.11.2026:

- **имя архива берётся из ответа команды** (`backupFile`), а архив лежит в подкаталоге по имени базы.
  Маска вроде `ls *-backup-*.zip` его не найдёт вовсе, а если найдёт похожий — проверите вчерашний
  архив вместо сегодняшнего и получите «успешно» там, где снимок не делался;
- **забранный архив удаляется из тома.** `BACKUP DATABASE` пишет в тот же том, что и сам пакет; если
  не убирать, он растёт до конца диска. Удаляется ровно тот файл, что забрали, — предмиграционные
  архивы, если они лежат в том же томе, остаются на месте.

**Как проверить — развернуть снимок в одноразовый контейнер.** Рабочая база при этом не трогается:

```bash
D=/opt/lore-backups/$(date +%F)
read -r DB F < "$D/MANIFEST"         # первая база этого прогона; для другой — своя строка MANIFEST
docker run -d --name arc-restore-test -p 127.0.0.1:12480:2480 -v "$D":/backups:ro \
  -e JAVA_OPTS="-Darcadedb.server.rootPassword=restore-check-only \
     -Darcadedb.server.defaultDatabases=$DB[root]{restore:file:///backups/$F}" \
  arcadedata/arcadedb:26.11.1       # версия — та же, что в .env пакета (ARCADEDB_VERSION)
until [ "$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:12480/api/v1/ready)" = 204 ]; do sleep 2; done
curl -s -u root:restore-check-only -H 'Content-Type: application/json' \
  -d '{"language":"sql","command":"select name, records from schema:types order by name"}' \
  "http://127.0.0.1:12480/api/v1/command/$DB" > /tmp/after.json
docker logs arc-restore-test 2>&1 | grep -q 'Full restore completed' && echo 'восстановление завершено'
docker rm -f arc-restore-test
```

Сравните числа из `counts-<база>.json` и `/tmp/after.json`: по каждому типу они обязаны совпасть. У нас такая
проверка на настоящем снимке дала 17 типов и 28 669 записей до и после — расхождений ноль.

### 4. Свой Keycloak — или честно без входа

**Что это.** LORE умеет вход через OIDC, но провайдер должен быть ваш: пакет его не ставит.

**Что будет без этого.** Установка работает БЕЗ входа: кто открыл адрес — видит всё. Для домашнего стенда это
нормально, для машины, доступной извне, — нет. Телефон miniLORE без входа не работает вовсе.

**Как сделать.** Поднимите Keycloak (или другой провайдер OIDC), заведите клиент `lore-app` (public, PKCE S256,
redirect на адрес вашего веба) и укажите в `.env`: `LORE_AUTH_ENABLED=true`, `LORE_OIDC_ISSUER=<адрес области>`,
`LORE_OIDC_ORIGIN=<адрес Keycloak>`. Повторите `install.sh` в тот же каталог — это обновление, пароли
сохраняются. Подробности — раздел «Keycloak — вход по выбору».

**Как проверить.** В вебе должна появиться кнопка входа, а `/lore/whoami` после входа — вернуть ваше имя и роль,
а не «не определён».

### 5. Зеркало базовых образов

См. «Требования»: `LORE_IMAGE_REGISTRY` для образов, которые пакет запускает, и `registry-mirrors` в настройках
docker — для сборки из исходников. Нужно, если у машины нет доступа к Docker Hub: иначе установка встаёт на
первом же образе.

## Хранилище файлов

Своего хранилища пакет не ставит: Docker Hub перестал отдавать образ MinIO (21.11.2026). Выбор — флаг `--files`:

- **`--files none`** (по умолчанию) — без файлов. LORE работает; загрузка и показ вложений, аватаров и ассетов BRAGI отвечают «хранилище файлов не подключено» (503).
- **`--files s3`** — своё S3: адрес, регион, бакет и ключи в окружении или в `.env` (`S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`). До запуска установщик проверяет связь: кладёт пробный объект и читает его обратно; не вышло — останавливается с причиной.

Бакет один на все файлы: ключи разведены приставками — ассеты LORE `<тип>/<код>/…`, BRAGI `bragi/…`, аватары `user/…`.

Чего в этом профиле нет:

- **Секрета клиента для бэкенда и веба.** Бэкенд проверяет токены как сервис (`quarkus.oidc.application-type=service`). Веб — публичный клиент `lore-app` с PKCE, поэтому `LORE_OIDC_ISSUER` и `LORE_OIDC_CLIENT_ID` — адреса и имена, а не секреты.
- **Infisical для секретов самого LORE.** В установке `lore.secrets.provider=env`: бэкенд читает свои секреты из окружения контейнера, то есть из `.env`. Infisical здесь нужен только по выбору и только для записи секретов учёток MCP (см. «Keycloak — вход по выбору»).
- **`LORE_VOLVA_EMBED_SECRET`** (временная подпись HS256). Профиль его не передаёт. Без пары ES256 встройка Völva отвечает «не настроено».

## Версии и образы

Инсталлятор ставит **только мажорные версии** `vX.Y.0` (решение владелицы 14.11.2026; то же правило, что у публикации на GitHub). Для такой версии образы берутся готовыми из GitHub Container Registry — `ghcr.io/nooriuta/lore-backend:vX.Y.0` и `ghcr.io/nooriuta/lore-web:vX.Y.0`, без входа. Публикует их релизный workflow при мажорном теге — те же образы, что прошли препрод и прод.

```bash
bash deploy/install/install.sh --version v1.18.0            # готовые образы из ghcr
bash deploy/install/install.sh --version v1.18.0 --build    # собрать из исходников тега на месте
```

Патч (`v1.17.21`) и rc — отказ с причиной. Без `--version` инсталлятор собирает из рабочего чекаута (`--src`) — это путь разработки.
