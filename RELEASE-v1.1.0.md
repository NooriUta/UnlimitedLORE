# v1.1.0 — RBAC: агент действует от имени владельца

Minor-релиз: изменилась модель прав. Закрыт спринт `SPRINT_LORE_ADMIN_PANEL` (55 задач, эпик ADR-LORE-036) — админка доведена от «витрины» до рабочего контура: живой Keycloak, аудит, SCD2-история правок, и главное — агент больше не «просто admin», а исполнитель, чьи права выводятся из роли его владельца в конкретном проекте.

## RBAC-эпик (ADR-LORE-036): цепочка client_id → владелец → роль → делегирование

До этого релиза любой MCP-агент с realm-ролью `admin` писал куда угодно — граф не знал ни чей это агент, ни в каком проекте тот имеет право работать. Теперь:

- **Человек — вершина графа** (AL-82): `KnowPerson` с ролью в проекте (`HAS_PROJECT_ROLE`), а не строка в Keycloak.
- **Агент привязан к владельцу** (AL-83): `KnowActor.client_id` + ребро `OWNED_BY` — по `client_id` из токена восстанавливается, чей это агент.
- **Резолвер прав** (AL-68): `client_id → владелец → его роль в проекте → матрица делегирования D4` (owner делегирует все 8 профилей; architect — architect/developer/tester; pm — pm/product-analyst/analyst/tester; и т.д.).
- **Первый write-путь под D4** (AL-90): семейство `actor` — агент пишет в проект только если роль его владельца там делегирует его профиль. Отказ — честный `AGENT_SCOPE_FORBIDDEN` с причиной.
- **Создание проекта — только super-admin** (AL-84 п.1): семейство `project` целиком в `HUMAN_ONLY`, агентам недоступно независимо от ролей.
- **Реальный Keycloak приведён к модели** (AL-66): realm-роль `admin` снята с 7 узких агентных клиентов — осталась только у `lore-mcp-full`. Выполнено владельцем вручную, пофактно сверено.
- **Задокументированное следствие** (SPEC-RBAC-OMILORE-AGENTS §10.5): `requireAdmin` срабатывает раньше D4, поэтому узкие профили после AL-66 блокируются ещё до проектной проверки — D4 сегодня фактически ограничивает `agent-full`. Это не баг, а пересечение двух верных решений; пересмотр гейта для узких профилей — отдельной работой.
- **Тесты**: `quarkus-test-security-jwt` в тест-контуре, `LoreActorProjectRbacWiringTest` — REST-раунд-трипы с эмуляцией JWT-клеймов (владелец-owner ✓, чужой проект ✗, агент-сирота ✗, узкий владелец не делегирует широкий профиль ✗, человек мимо D4 ✓).

## Админка: от витрины к рабочему контуру

- **Аудит-лог** write-операций по осям human|agent / роль / семейство / сущность + слайс (AL-20).
- **История правок словаря** — SCD2 (`KnowDictEntryHist`), кто и когда менял справочник (AL-43); история задач показывает дифф по всем версионируемым полям, не только статус (AL-30).
- **Регресс-гвард матрицы прав**: захардкоженная копия матрицы в тестах ловит любое расхождение с боевой; оси `agent_scope` и `seer_roles` разделены и проверены тестом (AL-47).
- **Тег-справочник един**: `LoreTag` слит в `KnowTag`, дубли схлопнуты (AL-29).
- **Статусы решений из словаря-канона** (AL-79/AL-86) + два принятых решения: схемы id `-D<n>`/`-R<n>` не унифицируются (D-2026-169); легаси-статусы мигрируют в канон, при понижении статуса ADR дочерние решения понижаются вместе с ним (D-2026-170).
- **CD-гейт KC-моста** (AL-88, шесть попыток): реальная причина — пробел после двоеточия в JSON, который не учитывал паттерн проверки. Попутно: гейт через throwaway-контейнер, окно ожидания растянуто, тайминги Infisical в логе.

## Фронтенд

- **401 не от бэкенда доводит до входа** (AL-85): `assertJson` стоял ДО проверки статуса на всех 26 call-site'ах — HTML-ответ прокси/Keycloak ронял «LORE недоступен» вместо экрана входа. Плюс экраны BRAGI различают «ошибка» и «пусто», обзор BRAGI грузит три слайса независимо — падение одного не гасит остальные.
- **Редактор ADR — попап** (AL-97): Mantine Modal вместо подмены целой панели, связи на `LoreLinkChips`, в форме появилось поле «Проекты» — раньше проект нельзя было привязать при создании вовсе.
- **Проектный скоуп в шапке** (AL-78): декоративный tenant-переключатель (DEFAULT/DEMO) заменён реальным выбором проекта — персистентным, с реконсиляцией удалённого slug; пока влияет на План и Вехи (единственный project-scoped слайс — `sprints`).
- **Поле «Обоснование» — TipTapField** (AL-89), форма правки вопроса — попап, открытие вопроса с ответом грузит решение, Admin-вкладки не падают в вечный 401 при включённой auth.

## Аналитика (AN-01..AN-11)

Семь новых read-слайсов и экраны над ними: VP-fit ядро с реестр-тестом паритета, `product_hygiene` (гигиена связок одним срезом), `strategic_coverage` (дыры покрытия в обе стороны), `invest_profile`, shipped-динамика, карта нагрузки ролей, распределение линтер-оценок.

## Продуктовый слой (SPRINT_LORE_PRODUCT_FIT, частично)

Ранг выгоды и связи `BLOCKS`/`SUCCESS_OF` задаются из формы, а не только через MCP (FIT-01); пикер работ с поиском вместо плоского списка (FIT-08); плашка «тестовая база» в шапке — признак приходит от самого бэкенда, подделать конфигом фронта нельзя (FIT-05); тест-страж на рёбра VP-канвы (FIT-06).

## Инфраструктура и релизный контур

- **Telegram-оповещение о публикации релиза** (TG-01); CD-уведомления несут заголовок PR («что именно выехало») и публичные ссылки.
- **Проверка токена зеркала** GitHub понимает fine-grained PAT, вердикт приходит в Telegram; ручной прогон релизного workflow.
- **CI-01**: тест-БД выбирается по типу события — push и pull_request больше не делят одну базу (источник флейков).
- **Миграции**: V14 переписан аддитивно (ось совместимости 13.1), сидер компонентов встроен в цепочку готовности раннера (MIG-31), ручной `docker compose up` не тушит auth молча (MIG-32), KC-мост ретраится при старте (MIG-33).
- `release_unlink` больше не падает 500-й: `DELETE EDGE` отсутствует в грамматике ArcadeDB 26.7.2 — обход через `DELETE FROM` по `@rid`.

## Известные ограничения

- Узкие агент-профили (architect/pm/…) полностью блокируются `requireAdmin` до достижения D4 — пересмотр гейта заведён отдельной работой.
- Проектный скоуп чтения (`project=null` → «все разрешённые», а не буквально все) — впереди, фаза `PHASE_PROJECT_SCOPE` (AL-91…AL-96): рёбра project для docs/runbooks, резолвер allowedProjects, фильтры слайсов, UI-разрывы из аудита AL-96.
