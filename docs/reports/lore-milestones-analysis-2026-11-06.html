Ценность и исполнение: что показали релизы, фичи и сценарии

Шесть исследований роя агентов 06.11.2026. Каждое пересчитано независимым проверяющим, который пытался его опровергнуть; ниже — уже с его поправками. Метка у каждого блока: подтверждено · с поправками · вывод опровергнут.

Главное из шести исследований (все проверены)
  1. Ценность прослеживается почти только у LORE. До сценария или фичи доходят 209 из 4 053 закрытых задач в релизах (5,2%) и 37 из 480 релизов. У 48% закрытых задач класс работы не размечен вовсе — для AIDA апреля–мая вопрос о ценности сейчас не решается, а не «ценности не было».
  2. Канва ценности закрыта только у LORE. Все 21 обещанная, но не начатая боль — у MIDGARD (17 из них high). Из 9 обязательных выгод доставлено 4.
  3. Bus factor студии — один человек, владелица. 98% исполнения — агент, 75% приёмок — владелица. Но тренд «гейт снизил самоприёмку» не наблюдаем: половина ролевых рёбер загружена одним скриптом 31.08.
  4. Половина релизов — сборочный поток, а не поставка. 234 из 480 вышли пачками по 5+ в день, почти все — miniLORE. Фичи ровно поставляет только LORE. AIDA почти перестала релизиться после июня. Ни один релиз не анонсирован через BRAGI.
  5. Поправочного коэффициента к оценкам нет: 75% закрытых задач ни разу не были «в работе», измеримых — 14%, разброс факт/оценка — десятки раз. Прогноз пока — по пропускной способности.
  6. В графе много мусора: 51 заглушка-спринт с одной задачей T-01 в семействе AIDA, фантомный релиз AIDA v1.8.0, 20 дублированных рёбер «спринт → релиз», 17 повторяющихся release_id, у релиза v1.5.0 две открытые строки истории.

Почему так. Цикл по истории статусов отражает момент записи статуса, а не трудоёмкость: три четверти задач закрыты без рабочего статуса, треть измеримых — за минуты, в цикл входят ожидание ревью и деплоя, ночи и пакетные правки. Медиана дала бы недопланирование в разы, итог по сумме — абсурдное перепланирование.

Что делать для квартального прогноза:

  • Сейчас — планировать по пропускной способности, а не по Σ оценок × коэффициент: сколько задач и какой суммы оценок закрыто за прошлые кварталы (без пакетных закрытий).
  • Начало работы фиксировать по факту: переход «в работу» — в момент начала; PLANNED → DONE без рабочего статуса помечать флагом.
  • Уборочные правки статусов помечать флагом bookkeeping в строке истории, а не угадывать по пакетным минутам.
  • Фактические затраты — отдельным полем (actual_days или время сессии агента при закрытии); ожидание приёмки — статусом review (он уже есть в едином workflow ADR-LORE-044) и не включать в работу.
  • Роль исполнителя и класс работы записывать всегда.
  • Перепроверить через квартал: коэффициент можно брать, когда p75/p25 внутри типа задач не больше ~3 (как сейчас у research и uc).

У каждого продукта своя карта на одной временной шкале. Слева — история: серии релизов (у 91% закрытых спринтов есть релиз). Справа — прогноз по кварталам: веха стоит в квартале в порядке зависимостей. Отмечены ревизии в начале каждого квартала и сегодняшняя дата.

Как читать прогноз

Длина полосы — квартал планирования, а не обещание дат внутри квартала. В подписи — оценка открытых задач в человеко-днях и её покрытие: «27 ч/д · 25 из 47» значит, что оценены 25 задач из 47. Если оценок нет, стоит «не оценено». красным отмечены вехи, у которых нет декомпозиции или которые ждут решения. На ревизии прогноз двигается, причина сдвига остаётся в истории вехи.

Что меняется в правилах вех

  • R3 (прогноз): у регламентной работы прогноз — период (месяц/квартал), а не дата завершения.
  • R12 (веха без задач): для воронки — «веха без кампании и целевого числа» (например, «15–20 контактов в месяц, 1 LOI»), а не «без задач».
  • Done-гейт: приёмщик ≠ исполнитель остаётся для всех; добавляется доказательство по виду работы (документ, LOI, URL, протокол) — аналог релиза.
  • Скорость и портфель считаются по ядру и только по done с доказательством — так не повторится «45 закрытий за два дня».
  • Типы задач: добавить sales, support, legal, finance, procurement, hiring — иначе стадия цепочки ценности по-прежнему угадывается по названию.
Унификация — записано в ADR и спеку

Да, workflow унифицируется. Шесть видов работы выше — это не шесть автоматов, а один канон (planned · active · waiting · review · done · failed · blocked · cancelled), стадия внутри active/waiting и доказательство done своего вида. Записано: ADR-LORE-044 (PROPOSED), его решения D-2026-LORE-UNIFIED-WORKFLOW-CORE, D-2026-LORE-DONE-NEEDS-EVIDENCE, D-2026-LORE-SERVES-EDGE, D-2026-LORE-PROJECT-WITHOUT-REPO, D-2026-LORE-PRODUCT-KINDS-TECH-SERVICE и спецификация SPEC-LORE-WORK-ANY-KIND с порядком внедрения для будущего спринта.

Вердикт GOAL/KAOS по не-ИТ работе

Цель: любая работа студии — разработка, учёт, продажи, регуляторика, железо — видна в одном плане, с честным статусом и доказательством результата. Главное препятствие: один набор статусов разработки на всё, поэтому не-ИТ работа либо врёт (CFP «planned» после дедлайна), либо не заводится вовсе (FREYJA — 2 задачи на 14 спринтов, A1 — 0).

Препятствия к самой схеме и обход: агент выберет не тот вид работы → вид по умолчанию от типа продукта и типа задачи, линтер сверяет; waiting станут прятать застой → проверка «waiting 30+ дней»; отображение в ядро теряет детали → портфель видит ядро, продукт — свои статусы; BRAGI уже свой → не дублировать, только отобразить его статусы в ядро.

Must: состояния waiting и failed в едином каноне, доказательство done по виду работы. Should: справочник стадий и поле workflow на спринте только для переопределения; новые типы задач. Could: своя сущность воронки продаж в HARPA, когда объектов станет много.

Схема меняется (статусы waiting и failed, справочник стадий, поля stage/evidence) — записано в ADR-LORE-044 и SPEC-LORE-WORK-ANY-KIND; внедрение — отдельным спринтом.
