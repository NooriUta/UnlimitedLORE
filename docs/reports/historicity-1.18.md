# Историчность в модели 1.18 — все типы и связи

19.11.2026 · SPRINT_LORE_MODEL_DOCS_TIDY/MDL-02 · ветка `feat/historicity`

Основание: слова владелицы 15.11 в заметке задачи — «Типы без истории: списком все объекты, текущее состояние историчности, предложение» и «История рёбер: версии рёбер, кажется, ведутся в самом ребре, проверь». Её решения 15–16.11 из книги «Декларация модели» (`scripts/model-migration/tools/decl/hist-table.json`, `decisions.cjs`) взяты как есть и помечены «решено».

Откуда цифры:
- «Записей / версий / с историей» — копия ryzenai, база `migration_dst_rehearsal` (ArcadeDB 127.0.0.1:2495), только SELECT, 19.11.2026. «С историей» — записи, у которых больше одной версии (`out('HAS_STATE').size() > 1`); «без версии» — записи вовсе без версии.
- «Историчные поля» — признак `historic: true` у полей типа в `shared/model/lore-model.json`; плюс 14 служебных полей версии одним общим перечнем (valid_from, valid_to, state_uid, content_hash, changed_by, changed_by_kind, status_category, status_known_from, status_backfilled, source_commit, hist_for, created_at, updated_at, origin) — по типам они не повторяются.
- Типы без Hist-типа на копии пока не ведут историю вовсе: «решено включить» означает, что тип версии создаст генератор схемы при переносе (решение 15.11: признак у типа и полей в модели, тип версии выводится).

## 5. Связи с историей в самом ребре

Проверено 15.11 и повторно 19.11 на копии: версии в ребре ведёт только ROLE_HELD_BY. Решение владелицы 15.11 («согласна», книга, `decisions.cjs` строка «История рёбер»): признак «историчная» у связи в модели даёт на ребре «действует с» (valid_from) и «действует по» (valid_to). Сделано в этой ветке: раздел `edge_history` модели — одно описание на все связи (поля версии и список связей с причиной).

| связь | что связывает | рёбер на копии | valid_from / valid_to сейчас | станет |
|---|---|---|---|---|
| ROLE_HELD_BY | задача → человек / агент (автор, исполнитель, ревьюер) | 11148 | 11148 / 119 закрытых | историчная (уже) |
| IN_PHASE | задача → фаза | 1070 | 0 / 0 | историчная |
| TARGETS_MILESTONE | спринт, фича → веха | 731 | 0 / 0 | историчная |
| HAS_PROJECT_ROLE | человек → проект, роль свойством | 32 | 0 / 0 | историчная |
| FILLS_ROLE | агент → роль продукта | 5 | 0 / 0 | историчная (это «роль продукта в проекте» — допущение, см. вопросы) |

Как ведётся: новое ребро — `valid_from = сейчас`; смена или снятие — прежнее ребро закрывается `valid_to = сейчас`, новое открывается; «текущие» — только `valid_to IS NULL`. При переносе valid_from берётся по убыванию точности: своё у ребра → момент создания ребра → первая версия записи, от которой идёт связь → момент создания этой записи → момент переноса; источник считается в отчёте переноса.

Остальные связи — без истории (решение 15.11: «остальные — нужна доп. аналитика»). Кандидаты на следующий разбор (предложено мной): PART_OF задачи → спринт (перенос задачи между спринтами сейчас видно только по task_mv), BELONGS_TO / BELONGS_TO_PROJECT (смена компонента и проекта), OWNED_BY (агент → владелец, сейчас «снести и поставить»).
