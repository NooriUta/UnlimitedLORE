## 2. Правила, которые нельзя нарушать

- В `develop`, `preprod`, `main` напрямую не пушить: только ветка `feature/*` или `fix/*` и PR.
- Мерж в `develop` — только по зелёному CI. Проверять обе проверки, Backend CI и Frontend + MCP CI, через `forgejo-mcp get_commit_status` по SHA.
- Промо `develop → preprod` можно делать самому.
- **Релиз в `main` и тег — только по явному «да» владелицы.**
- **`./gradlew test` локально не запускать:** он мигрирует общую схему БД. Локально — только `cd backend && ./gradlew compileJava compileTestJava`, доказательство — CI на PR. `gradlew` лежит в `backend/`.
- Сборки и всё, что идёт минуты, запускать в фоне.
- Тест пишется до правки: сначала падающий тест, потом код до зелёного. В отчёте — дельта зелёных тестов.
- Инварианты UI, которые валят CI, но не ловятся `tsc`:
  - шрифты — только `var(--fs-*)`;
  - каждый ключ `t('…')` должен быть и в `ru`, и в `en` `common.json`;
  - MD-поля — `TipTapField`, тела — `MartProse`.
- LORE пишем только через MCP. Прямые правки базы — только с явного разрешения владелицы, сначала на препроде и с бэкапом.
- Пароли и секреты не вводить и не читать. Заблокировано — пиши громко блоком BLOCKED: что, зачем, как разблокировать.
- Корень проблемы раньше симптома. Непроверенное помечай как гипотезу.
- «Пусто» не равно «не смогли проверить»: отрицательный результат подкрепляй положительным контролем.
- Каждую найденную задачу или решение заводи в LORE и называй её ID в ответе.
