UI LORE v2: как аккуратно жить с двумя приложениями

08.11.2026 · исследование к ADR-LORE-045 (PROPOSED) · только чтение: код репо UnlimitedLORE (ветка feat/ve2-volva-embed-sign, совпадает с develop по затронутым файлам), miniLORE (app_flutter), LORE-слайсы, веб-источники · [гипотеза] = не проверено замером
TL;DR
  • Рекомендация: v2 — на отдельном поддомене lore-next.odal.seidrstudio.pro через Traefik (свой роутер и сервис lore-app-next), тот же lore-backend, тот же KC-клиент lore-app с добавленными точными redirect URI. Отдельный origin бесплатно разводит localStorage и сессию OIDC; общая cookie темы seer-prefs остаётся общей (так и задумано).
  • Отдельный порт отпадает: на http://IP:порт вход по OIDC физически невозможен (PKCE требует crypto.subtle = защищённый контекст). Путь /next возможен, но тянет base-path в Vite/роутер/redirect и общий localStorage — дороже и рискованнее.
  • Главная находка: MCP ходит в бэкенд через nginx фронта (LORE_BACKEND_URL=http://192.168.3.131:4400). Кто держит :4400, тот держит MCP. Значит прокси /lore/, /bench/, /tyr-* обязаны быть байт-в-байт одинаковы в обоих образах, а на переключении :4400 не трогаем.
  • Поправка к посылке ADR: miniLORE не строит веб-ссылки /lore?section=… — lore_refs.dart только находит id в тексте, а запись открывается в самом приложении через шлюз. Веб-ссылки в старом формате рождаются в заметках релиза (release-html.sh:55), Telegram, телах доков и ответах сессий — их и защищает нормализатор.
  • Фриз v1 — предлагаю каталогом, а не долгой веткой [предложение, нужно решение владелицы]: v2 растёт в web-next/ того же develop, v1 остаётся в src/ под сторожем «только багфиксы». Один конвейер, один preprod, никаких двух веток с расходящимся бэкендом.

Бэкенд: правила расширения

  • Expand → migrate → contract (Fowler, Parallel Change): новое поле/эндпоинт добавляется рядом, v1 продолжает читать старое; удаление старого — только после выключения v1 и отдельным PR.
  • Только аддитивные миграции. Любой ./gradlew test мигрирует прод-схему, т.е. схема может уехать вперёд работающего бэкенда ещё до мержа. Значит каждая миграция обязана быть безопасна для текущего прод-бэкенда: новые типы/свойства/индексы — да; переименование, смена типа, NOT NULL без дефолта, удаление — нет (это фаза contract).
  • Ответы — только расширять: новые поля в JSON можно, переименовывать/убирать/менять смысл нельзя; новые параметры слайса — необязательные с прежним поведением по умолчанию.
  • Запись — через общий сервис SCD2 (ADR п.4), одинаково для v1, v2, MCP, miniLORE; никаких «v2-only» обходных INSERT.
  • Контрактные тесты на каждый PR бэкенда (блокирующий гейт):
    • MCP: снимок списка инструментов + форма ответа ключевых (query_slice, search, task_new, status_set, lore_version) против бэкенда PR; есть зачаток — LoreQgRunContractTest.java.
    • Телефонный API miniLORE: /lore/news, слайсы и открытие по id для 18 типов (ET-01) — снимки форм ответа.
    • Старые веб-ссылки: таблица section × passport → v1 и v2 открывают ту же запись (Playwright, smoke).
    • Völva: /lore/embed/volva/{chart} — 200 своим, отказ служебному клиенту, проект заперт массивом.
    • Диф схемы ответов (снимки JSON или OpenAPI + oasdiff) против базы develop — информационный, падающий только на удалении/переименовании.

Данные пользователя

  • Неймспейс ключей: v2 пишет только lore.v2.* через одну обёртку storage.ts (запрет прямого localStorage линтером). v1 не трогаем — его ключи (список выше) считаем lore.v1-наследием; v2 может читать их один раз для импорта (проект, тема), но не писать.
  • На поддомене коллизий нет физически, но префикс всё равно нужен: на переключении v2 переедет на origin v1 и встретит его старые ключи.
  • Cookie seer-prefs — общая платформенная, формат {theme, palette} заморожен (expand-only), её читает и тема KC.
  • Серверные настройки по D-2026-UXR-VIEWS-SERVER: виды, избранное, личные умолчания (D-2026-UXR-RAIL-OFF, D-2026-UXR-READ-COLLAPSE) — на сервере, с полем ui_version/схемой версии у записи; v1 их не видит и не ломает. Это и есть «переносимость» между v1 и v2 и между устройствами.
  • Черновики (bragi-draft-*) — не мигрируем, предупреждаем в v1 баннером перед переключением [гипотеза: объём реальных черновиков мал].

CI/CD

  • Один конвейер, два образа: в compose новый сервис lore-app-next (build context — web-next/, тот же nginx.conf.template, без публикации хост-порта или только 127.0.0.1), роутер в traefik-оверлее.
  • Шаг which в lore-cd.yml расширить: frontend-next; dispatch-параметр service получает третье значение.
  • Сначала preprod (как сейчас): v2 живёт только на стенде до решения о переключении; v1-образ продолжает собираться из src/.
  • nginx-шаблон — общий файл для обоих образов (не копия), чтобы прокси MCP не разошлись; health-check деплоя для v2 — тот же curl 127.0.0.1/, плюс проба /lore/version через контейнер v2.
  • Frontend CI: отдельный job для web-next/ (tsc, vitest, STYLE-01, i18n-coverage); сторож «в src/ только fix-коммиты» — информационный, не блокирующий.
  • Если владелица оставит вариант ADR «ветка release/ui-v1»: тогда нужен второй workflow, собирающий только lore-app из этой ветки, и запрет CD собирать lore-app из preprod — иначе первый же preprod-деплой выкатит недоделанный v2 на место v1. Это главный аргумент за каталог.

Переключение и откат

  1. Фаза «проба»: v2 на lore-next, флаг «новая навигация» в меню аватара v1 = ссылка на v2 с текущим адресом (через нормализатор); в v2 — «вернуться в классический» (как GitHub Feature Preview / Atlassian Labs).
  2. Фаза «по умолчанию» (Atlassian: admin → opt-in/out → always-on): владелица решает дату; в v1 баннер «через N дней основной — v2».
  3. Переключение: Traefik-роутер lore переводим на сервис v2, а v1 получает роутер lore-classic.odal… (DNS + URI в KC + CORS заранее). Порт :4400 и его nginx-прокси (MCP) не трогаем до отдельного шага.
  4. Нормализатор ссылок в v2: любой старый /lore?section=X&passport=Y (и устаревшие tab) → новая схема через history.replace, с таблицей соответствий в коде и тестом на каждую строку; неизвестное — честная страница «ссылка старого вида, открыть в классическом».
  5. v1 держим на запасном адресе 4–6 недель [гипотеза срока — по метрике откатов]; выключаем, когда переходов в classic < порога за 2 недели.
  6. Kill switch / откат = вернуть роутер lore на сервис v1 (одна метка, up -d --no-deps), без пересборки; заранее отрепетировать на preprod и записать runbook.
  7. Contract-фаза бэкенда — только после выключения v1, отдельными PR.
  8. :4400 (MCP) — последним шагом: либо остаётся за v1-nginx до конца, либо уходит v2-образу с тем же шаблоном; проба lore_version из MCP после каждого шага.

Серверный спринт

  • Сервис lore-app-next в compose + роутер/сервис в traefik-оверлее, общий nginx.conf.template.

  • lore-cd.yml: выход frontend-next, сборка/деплой/проба нового сервиса.
  • Проба CD: /lore/version через каждый фронт-контейнер (защита MCP).
  • Контрактные снимки MCP-инструментов против бэкенда PR.
  • Контрактные снимки API miniLORE (/lore/news, открытие по id, 18 типов).
  • Контракт-тест Völva embed (свой/служебный/запертый проект).
  • Ревью-гард: миграции только аддитивные (чек в PR-шаблоне + тест на запрещённые DDL).

  • Runbook «переключение и откат одной меткой Traefik», репетиция на preprod.
UI-спринт
  • Каркас web-next/ (Vite, свой Dockerfile, CI-job, STYLE-01, i18n).
  • Обёртка storage.ts с префиксом lore.v2.* + lint-запрет прямого localStorage.
  • Одноразовый импорт из ключей v1 (проект, тема) без записи в них.
  • Нормализатор старых ссылок + тест на всю таблицу соответствий.
  • Смоук «старая ссылка открывает ту же запись в v1 и v2» (Playwright).
  • Флаг «новая навигация» в меню аватара v1 и «классический вид» в v2.
  • Обработка vite:preloadError (одна перезагрузка с защитой от цикла).
  • Сторож «в src/ только fix» (информационный).
  • Баннер в v1 о дате переключения и о несохранённых черновиках BRAGI.
