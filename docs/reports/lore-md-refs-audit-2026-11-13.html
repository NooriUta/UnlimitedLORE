Что стандартизировать для новых фич

  1. Одна форма записи — [[тип:ID]]. Это единственная форма, которую понимают все читатели: веб (kit MartProse), miniLORE и серверные автосвязи (MD-AUTOLINK). Сейчас ею записано 320 упоминаний из 23 054 (1,4%); [[ID]] без типа — ещё 3 366. Предложение: MCP-инструменты записи и редактор при сохранении переписывают узнанные формы в [[тип:ID]]; голая форма и тип:ID остаются читаемыми, но заново не пишутся.
  2. Задача — только парой СПРИНТ/КОД. 7 640 упоминаний одиноких кодов (7 169 в прозе, 471 в [[…]]); 17,5% неоднозначны — такой код есть у нескольких задач; 46,2% — код задачи своего же спринта. Предложение: при записи тела дописывать спринт владельца к коду своего спринта (PU-09 → [[task:SPRINT_…/PU-09]]); чужой одинокий код — предупреждение «назовите спринт», без молчаливой догадки.
  3. ID не в обратных кавычках. 1 388 упоминаний ID внутри `кода` — ни один читатель не делает их ссылкой. Предложение: правило агентам уже есть (CLAUDE.md), не хватает проверки: ID узнаваемой формы в inline-коде → предупреждение в ответе MCP с готовой заменой. Блоки кода ``` (165) не трогать — там примеры.
  4. Не URL экрана вместо ссылки на объект. 44 ссылок вида :4400/lore?…passport=…/new.lore…?open=… — адрес меняется при переезде (уже было: localhost → ci-server → new.lore), объект — нет. Предложение: при записи переписывать такие URL в [[тип:ID]].
  5. Красная ссылка — сразу при записи. 90 явных ссылок ([[…]] / тип:ID / @) ведут в никуда, ещё 554 голых ID «по виду» не находят записи (часто локальная нумерация вроде UC-1 или шаблон SPRINT_X/CODE). Предложение: ответ записи любого MD-поля отдаёт список битых (как mentions.skipped в MD-AUTOLINK, который сейчас есть только у ADR, решений, доков и спринтов).
  6. Вид ID не должен врать о типе. 96 упоминаний, где вид называет один тип, а запись другого (adr → decision: 94; sprint → task: 2). Главный случай — атомарные решения с ID ADR-…-Dn: Peek в вебе (typeByForm) и miniLORE по виду идут к ADR и показывают «записи нет». Предложение: для новых решений — только D-ГГГГ-…, а у старых ADR-…-Dn ссылаться формой [[decision:ID]]; правило вида ADR- в разборщиках — «ADR-X-N» без хвоста -Dn/-Rn.
  7. Один разборщик на всех. Формы разбираются тремя разными кодами с разным охватом (таблица ниже): веб делает ссылкой только [[…]] и узнаёт по виду 4 семейства, miniLORE — все формы и 17 типов. Предложение: одна общая таблица семейств и типов — источник для kit, web-next, сервера и этого аудита.
  8. Экранированные \[\[…\]\]. 1 — след сериализатора без markdownLossless; ссылка в них потеряна. Держать в тесте сохранения TipTap.
Перепись существующих тел пачкой — отдельным решением владелицы (через MCP, по SCD2). Этот скрипт ничего не пишет.

Метод и ограничения

  • Поля: свойства с окончанием _md, _md_ru, _md_en и description / summary / statement / text у всех вершин. У *Hist — только открытая версия (valid_to is null) и только поля, которых нет на самой вершине, чтобы текущее значение не посчиталось дважды. Рёбра (feedback_md у ROLE_HELD_BY) не читались.
  • Канон по SPEC-LORE-MD-INLINE-REF и правилу «Как писать идентификаторы LORE»: [[…]], тип:ID, по виду, tana. ID внутри блока кода — справка, не нарушение.
  • Одинокий код = токен, совпадающий с task_id существующей задачи. Коды, не заведённые в LORE, не ловятся — это нижняя граница.
  • Слаги доков и имена компонентов в прозе по виду не узнаются (вид не называет тип) — они видны только в [[…]] и тип:ID.
  • Детерминизм: отчёт строится только из снимка snapshot.json, всё отсортировано. Хэш снимка 662289e94ddfbf2e94549120cd8a767ee7f1cd4e7a1d5f19586aca092e095e1f. Повтор без базы: node scripts/md-refs-audit/audit.mjs --from snapshot.json.
