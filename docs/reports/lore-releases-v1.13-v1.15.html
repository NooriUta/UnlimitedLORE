Итоги периода

За девять дней LORE прошёл четыре релиза. Их общая тема — достоверность: система должна сообщать о фактическом положении дел, а не о формальном успехе операции.

  • Достоверный результат записи. Ранее операция записи могла вернуть ok:true, не изменив данных или, напротив, затронув соседние записи. Теперь ответ описывает фактическое изменение в графе (v1.13.0).
  • Ошибка загрузки больше не выдаётся за отсутствие данных. Экран, не получивший ответа, сообщает о сбое, а не показывает пустой список (v1.14.0).
  • Новая административная панель с поддержкой мобильных устройств и сохранением состояния экрана в адресе страницы (v1.13.1, v1.14.0).
  • Единый формат времени во всей истории изменений и однозначное время UTC в ответах API; переход на ArcadeDB 26.11.1 (v1.15.0).
  • Безопасность зависимостей: устранены 2 критические и 21 серьёзная уязвимость (v1.13.1).
Отчёт составлен по правилу описания релизов (decision:D-2026-LORE-RELEASE-NOTES-SHAPE): включены функциональные изменения и обновления технологий с указанием спринта и PR. Изменения инфраструктуры разработки и доставки (CI/CD) не включены. Версия v1.14.1 не выпускалась — её изменения вошли в v1.15.0.

Наименее заметный внешне, но наиболее глубокий релиз периода: изменён тип времени во всей истории изменений, а каждый срез данных получил постраничный режим и выбор полей.

Время в базе данных

Единый тип времени для всей истории изменений (миграция V56)

Проблема
В десяти из двенадцати типов истории изменений (*Hist) время хранилось строкой, в двух — датой. Встречались записи, где начало периода было строкой, а окончание — датой. Сравнение, сортировка и агрегирование по времени вели себя по-разному в зависимости от типа.
Решение
Поля valid_from и valid_to во всех двенадцати типах переведены в собственный тип даты ArcadeDB (DATETIME), как рекомендует документация СУБД. Миграция выполнена на рабочей базе 5 ноября за 17 минут. По каждому типу число заполненных значений до и после миграции совпало, нераспознанных значений и предупреждений не было; только по задачам обработано 12 278 записей.
Результат
Корректная выборка состояния на заданную дату, точный расчёт сроков и длительности спринтов, единообразная сортировка истории; функции минимума и максимума по времени работают без ошибок.
SPRINT_LORE_ROADMAP_PER_PROJECT/RM-P13 · #769

Время в ответах API — в однозначном формате UTC

Проблема
СУБД возвращает время без указания часового пояса (2026-04-13 00:00:00.000), а браузер интерпретирует такую строку как местное время. У пользователя в другом часовом поясе даты спринтов смещались на сутки.
Решение
Все JSON-ответы LORE возвращают время в формате ISO 8601 с явным признаком UTC: 2026-04-13T00:00:00.000Z. Формат на стороне СУБД намеренно не изменялся: проверка показала, что встроенная настройка формата в ArcadeDB формирует некорректную строку вида …171Z.171.
Результат
Одинаковые даты для всех пользователей и агентов — независимо от устройства и часового пояса.
RM-P13 · #768 · #769

Чтение данных

Постраничное чтение и выбор полей для любого среза данных

Проблема
Срез данных всегда возвращал результат целиком. Чтобы узнать текущий релиз, агент получал около 20 тысяч знаков описаний всех релизов.
Решение
Любой срез принимает параметры limit, offset и fields. Сокращённый ответ явно сообщает об этом в поле _page (лимит, смещение, общее число, наличие продолжения, выбранные поля). Ошибка в имени поля приводит к ответу 400 со списком допустимых полей.
Пример
releases?limit=1&fields=release_id,is_current — одна строка вместо полного списка.
Результат
Объём передаваемых данных сокращается в десятки раз; ИИ-агенты расходуют существенно меньше контекста.

Задачи и спринты

Защита закрытых спринтов

Проблема
Задачу можно было создать в уже закрытом спринте или перенести в него. В результате в двух закрытых спринтах Völva оказалось 11 незавершённых задач.
Решение
Создание и перенос задачи в спринт со статусом «завершён» или «отменён» отклоняются с ответом 400. Ответ содержит название спринта, дату закрытия и рекомендуемое действие. Изменять статус задач, уже находящихся в таком спринте, по-прежнему можно — чтобы их можно было завершить.
SPRINT_LORE_MEASURE_TRUTH/MT-SPRINT-DONE-GUARD · #770

Перенос, оценка и указание исполнителя

  • Перенос задачи сохраняет её статус. Ранее при переносе в другой спринт статус сбрасывался на «запланирована». #771
  • Оценку трудоёмкости можно задать при создании задачи, без отдельного вызова. Принцип: всё, что принимает изменение задачи, принимает и её создание. #758

Агенты и MCP

Агент с полными правами может работать в рамках узкого профиля

Проблема
Универсальный агент full всегда выполнял запись с полными правами — даже при работе в роли тестировщика или маркетолога.
Решение
Заголовок X-Lore-Act-As (в MCP — переменная LORE_ACT_AS) задаёт профиль, по матрице которого проверяется операция. Заявленный профиль может только сузить права, но не расширить их; профиль, закреплённый за собственным клиентом агента, заголовком не изменяется.
Результат
Соблюдение принципа минимальных привилегий для ИИ-агентов без отдельной учётной записи под каждую роль.

Каждая операция записи сообщает о фактическом результате

Проблема
Ответ ok:true означал лишь, что команды выполнились без исключения. Отсутствие изменений, повторное создание связи и удаление чужой привязки выглядели одинаково успешными.
Решение
Ответ содержит поле outcome — результат операции: создано, обновлено, без изменений, удалено или не применимо, с указанием причины. Значение определяется по фактическому состоянию графа после записи. Механизм распространён на спецификации, релизы, проверки качества, вопросы, регламенты, компоненты, справочники, проекты, пользователей и роли, файлы, продуктовый слой и автоматическую привязку Forgejo. Прежние поля ответа сохранены.
ADR-LORE-043 · SPRINT_LORE_DB_RESILIENCE/DBR-17 · #710 · #714 · #715 · #719

Устранённые случаи скрытого повреждения данных

  • Привязка спецификаций: замена на несуществующий объект удаляла действующую привязку и лишь затем возвращала ошибку 404; удаление непривязанного компонента снимало существующую привязку.
  • Дублирование связей: повторная привязка спецификации, релиза или PR создавала вторую связь — у спринта накапливалось по связи с релизом на каждое слияние.
  • Подсчёт связей релиза учитывал выполненные команды, а не созданные связи: несуществующий спринт отображался как привязанный. Привязка к несуществующему релизу завершалась внутренней ошибкой 500.
  • Проверки качества: запуск без проверки, рекомендация без запуска и перенос в несуществующий спринт создавали несвязанные записи при успешном ответе; повторный перенос создавал вторую задачу. Теперь — ответ 404 до записи, повтор не меняет данных.
  • Компоненты: изменение несуществующего компонента завершалось успешно; смена родителя сохраняла прежнего — у компонента оказывалось два родителя.
  • Продуктовый слой: недопустимая роль удаляла существующую связь до ответа с ошибкой 400.
  • Роли пользователей: назначение роли в незарегистрированном проекте фиксировалось в журнале без фактического создания связи.
  • Справочники: каждый повтор создавал пустую версию в истории.
  • Схема: отсутствовал индекс KnowPR(pr_uid) — на новой базе привязка PR к релизу завершалась ошибкой 400.

Анализ структуры задач

TaskShape — оценка полноты и сложности задачи по её описанию

Решение
  • шаблон описания: обоснование, шаги, критерий готовности, тест, проверка на рабочей системе;
  • класс сложности S/M/L/XL по набору факторов и сверка с оценкой трудоёмкости;
  • рекомендации: разделить крупную задачу, объединить мелкие, добавить шаги, проверку, тест, оценку;
  • подсказки в ответе на создание и изменение задачи — без влияния на оценку качества;
  • GET /lore/task-shape и MCP-инструмент task_shape — сводка по проектам для аналитики (Völva).
Калибровка
На выборке из 5310 задач медианная длительность растёт вместе с классом: S — 1,47 дня, M — 1,61, L — 2,88, XL — 6,83.
SPRINT_LORE_MEASURE_TRUTH/MT-TASK-SHAPE · #717 · #720

Доступ к базе данных и мониторинг

Работа с базой по отдельному токену без права изменения схемы

Проблема
LORE подключался к ArcadeDB общей учётной записью root. Один неверный пароль любого соседнего сервиса блокировал root для всех баз на сервере — так 31 июля была недоступна рабочая система. Перезапуск контейнера неявно применял миграции схемы.
Решение
Режим подключения lore.mart.auth = basic | token: рабочий процесс использует токен без права изменения схемы, а миграции применяются отдельным шагом, а не при запуске приложения. В режиме token без токена сервис не запускается — скрытого возврата к паролю нет.
Состояние
Реализация готова; токены выпущены 5 ноября. Переключение — после размещения токенов в хранилище секретов и подтверждения со стороны соседних систем.
