1в. Решение владелицы: раскладка зависит от того, где открыт паспорт

Правило (08.11): большой блок — вкладки с тем, без чего изменения не сохранить (текст, свойства, обязательные поля). Узкая колонка слева — только дополнительное, вычисляемое: связи, граф, журнал, история, Völva, состояние данных. Когда паспорт открыт панелью справа и места мало — левой колонки нет: всё уходит во вкладки основного блока.

Чем Б отличается от А
  • Свойства переехали к записи — сеткой под заголовком, рядом со статусом. Правятся там же, где текст. Колонки «Свойства» больше нет.
  • Правая зона — только вычисляемое: связи, граф, журнал, история, Völva, состояние данных. Подпись «только чтение» — сразу видно, что здесь ничего не правят.
  • Вкладки слева — только части самой записи: «Текст» и свои вкладки типа (у спринта «Задачи»).
  • Связь правится не в зоне «Вокруг», а полем свойств («Проекты», «Зависит от») — зона «Вокруг» показывает результат.
  • Обязательные свойства (у задачи — спринт, у спринта и ADR — ID, у связи — цель) стоят в зоне «Запись» сразу под заголовком. При создании они идут ПЕРВЫМИ, подсвечены «обязательно», и «Сохранить» неактивно, пока они пусты — с причиной текстом. Зона «Вокруг» у новой записи пуста по смыслу (её ещё нет в графе) и свёрнута. Какие поля обязательны — решает сервер (schema.fields[].required), а не kit.
  • На телефоне: «Запись» сверху, «Вокруг записи» — ниже свёрнутым блоком.
  • Контракт не меняется: schema.fields с group: props рисуются под заголовком, schema.tabs делятся на zone: record | around.

3. Контракт объекта паспорта — черновик для согласования

Принцип: один объект на любой тип записи. Поля, вкладки и права приходят от сервера, kit только рисует — новый тип или новое поле не требуют правки kit. Подписи — ключами локализации и текстом, с версией (решение 30.08.2026, SPEC-LORE-FIELD-LABELS). Всё — аддитивно, v1 не задевается.

GET /lore/record/{type}/_new             — пустой паспорт для создания (значения по умолчанию)
PATCH /lore/record/{type}/{id}           — правка: { expected_version, values: {…} }

Вопросы к согласованию с бэкендом
  • Схема полей — из какого источника: из описания параметров MCP-инструментов (sprint_new, adr_new, spec_new…), из модели вершин ArcadeDB или отдельный реестр? Подписи — по SPEC-LORE-FIELD-LABELS (ключ + текст + версия).
  • Запись — один эндпоинт на все типы или поверх существующих слайсов и MCP-инструментов (тогда /lore/record — фасад)?
  • version и 409 — общий механизм SCD2 для всех типов (как у настроек S2-09)?
  • Разрешённые переходы статусов (status_next) и права (can_*) — считает сервер по роли и проекту.
  • meta.sources — честные состояния по блокам (как полнота S1).
  • Черновик на сервере — /lore/me/drafts/{type}/{id} (рядом с S2 «что LORE помнит»)?

4. Как kit рисует объект

  • schema.fields → поля вида (сегодня KindConfig.fields пишет приложение — станет приходить с сервера); group решает, где поле: шапка, тело, «Свойства».
  • values → record.fields; facts → строка фактов (8); perms → есть ли ✎, «+ Создать», меню статусов; meta.loaded_at → (9); meta.sources → (16).
  • Место паспорта (справа / снизу / на всю страницу) — обёртка вокруг того же RecordReader, решается отдельно.

5. Согласование с сессией бэкенда (08.11, ответ 698f34c4)

  • Поля (schema.fields) — из одного реестра на бэкенде (Java): тип → поля, подписи по SPEC-LORE-FIELD-LABELS. Его читают и UI, и MCP. Описания параметров MCP — нет: они в TS-пакете, бэкенд их не видит, источников стало бы два.
  • Фасад /lore/record/{type} — ок для чтения (собирается из существующих слайсов). Запись — только через те же Java-сервисы, что вызывают MCP-инструменты; мимо них ломается SCD2 и слайсы.
  • version + 409 — сейчас есть только у /lore/me/views. У записей SCD2 проверки версии нет нигде: версия = ревизия открытой Hist-строки, проверку надо добавить в каждый путь записи. Это новая работа.
  • status_next и can_* — посчитать можно (граф ролей и скоуп есть). Но служебная учётка приложения не заведена в графе ролей: «нет прав» и «не опознан» сейчас неотличимы — в reason разделять явно.
  • Черновики — /lore/me/drafts/{type}/{id} рядом с views/memory, с тем же expected_version.
  • Решение — за владелицей, тянет на ADR: реестр полей на бэкенде + фасад чтения + проверка версии во всех путях записи.
