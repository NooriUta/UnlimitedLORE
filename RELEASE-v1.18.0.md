# LORE v1.18.0

Первый выпуск на новой модели. Схема базы теперь собирается из модели LORE, а данные переносятся в неё одним проходом, без потерь: на репетиции с копией прода совпали и число записей, и число связей. Связи помнят, когда появились и когда закрылись. В админке есть раздел, где видно, как прошёл перенос. Появились репозитории и организации. MCP работает по адресу хоста LORE, а входы в базу под root сторожит отдельная служба.

**Важно при обновлении.** Версия ставится только через перенос в новую базу: сначала бэкап, потом перенос, потом выкатка. Прежняя база при этом не меняется, на неё можно вернуться.

## Перенос на новую модель

- **Схема и база собираются из модели, данные переносятся одним проходом** (SPRINT_LORE_MODEL_DOCS_TIDY/MIG-01, #1619). Повод: схема прода годами наращивалась миграциями. У неё накопились поля, которых нет в модели, поля с разными именами для одного смысла и необъявленные типы. Из-за этого паспорта и срезы приходилось чинить по одному. Теперь база строится по модели заново. Каждый объект и каждая связь переносятся с проверкой. То, что не удалось привести к модели, не теряется: оно попадает в «остаток» с указанием причины. Ценность: одна модель для схемы, паспорта и клиентов. На репетиции 20.11 с копией прода (снимок 18.11) сверка «было = стало» сошлась по записям (задачи 6687 = 6687, их версии 17217 = 17217), по справочникам (67 из 67) и по всем девяти сверкам связей. Два прогона дали одинаковый отпечаток базы.
- **Перегруппировка проектов, вид продукта и «решение → веха» при переносе** (SPRINT_LORE_MODEL_DOCS_TIDY/MIG-01, #1619). Повод: проекты были заведены вразнобой, у продуктов не был указан вид (tech или service), решения без ADR не были привязаны к вехе. Теперь установщик предлагает группу для каждого проекта и вид для каждого продукта, а окончательный выбор делает человек. Веха решения вычисляется при переносе. Старую доску плана можно не переносить (настройка `MIG_PLAN_BOARD`, по умолчанию не переносится). Ценность: в новую базу данные приходят уже разобранными, без отдельной уборки после переноса.
- **Чтение и запись поверх новой схемы без смены клиентов** (SPRINT_LORE_MODEL_DOCS_TIDY/MIG-03, #1619). Повод: новая схема называет поля и коды статусов по-новому, а UI, MCP и miniLORE ждут прежний ответ. Теперь сервер сам переводит запросы к старым именам на новые и отдаёт ответ в прежнем виде, например `status_raw` и статусы строчными буквами. Ценность: после переноса клиенты работают без обновления.
- **Раздел админки «Перенос на новую модель»** (SPRINT_LORE_MODEL_DOCS_TIDY/MIG-02, #1619). Повод: чтобы узнать, как прошёл перенос, раньше приходилось читать JSON-отчёты на сервере. Теперь в админке видно этапы прогона (чтение → расчёт → сведение → запись → сверка). Расхождения и удержанные значения собраны в группы по причинам, со ссылками на записи. Правило переноса человек принимает здесь же, подтверждая его своим логином. Раздел честно различает состояния «прогона не было», «источник прочитан не весь» и «сверка не сошлась». Ценность: решения о переносе принимаются в интерфейсе, видно, кто и когда их принял.

## Модель

- **Связи помнят своё время** (SPRINT_LORE_MODEL_DOCS_TIDY/MDL-02, #1619). Повод: связь удалялась бесследно, поэтому нельзя было узнать, когда задача ушла из спринта или когда ADR перестал на что-то ссылаться. Теперь у связей есть `valid_from` и `valid_to`, и снятая связь закрывается, а не удаляется. Дата старой связи при переносе берётся по последнему обновлению её объектов. Ценность: история изменений охватывает и связи, а не только поля записи.
- **Типизация по модели и формат дат** (SPRINT_LORE_MODEL_DOCS_TIDY/MDL-06, #1619). Повод: даты хранились то днём, то моментом времени, и тип значения при записи никто не проверял. Теперь точность даты задаёт модель: `shipped_at` хранится днём, `status_known_from` — моментом времени. Если записывается значение не того вида, сервер предупреждает. Ценность: даты в паспортах и отчётах сравнимы между собой, а ошибки вида значения видны при записи, а не через месяц.
- **Репозитории и организации — свои объекты** (SPRINT_LORE_MODEL_DOCS_TIDY/MIG-03, #1619). Повод: адрес репозитория был полем проекта. Поэтому нельзя было ни показать зеркало, ни привязать отдельный репозиторий к компоненту. Теперь в группе «Система» есть разделы «Репозитории» и «Организации» с паспортами. У проекта и у компонента появилась вкладка «Репозитории». Роли репозитория: основной, компонент или зеркало. Ценность: видно, где лежит код каждой части продукта и какой репозиторий чьё зеркало.

## MCP и безопасность

- **MCP по адресу хоста LORE** (SPRINT_LORE_AGENT_OBSERVABILITY/AO-MCP-HOSTED, #1619). Повод: каждую новую версию MCP приходилось пересобирать локально на каждой машине, и версии на машинах расходились. Теперь MCP — сервис самого LORE по адресу `https://<хост LORE>/mcp` (Streamable HTTP). Клиент передаёт свой токен, профиль инструментов выбирается заголовком. Ценность: версия MCP всегда совпадает с версией LORE, а для подключения агента нужен только адрес и токен.
- **Сторож входов в базу под root** (SPRINT_LORE_PRODUCT_BACKLOG/DBR-07, #1619). Повод: ArcadeDB не записывает успешные входы в журнал, поэтому вход под root с неожиданной машины остался бы незамеченным. Теперь перед базой стоит сторож. Он записывает каждый первый вход «пользователь × источник» в ряд `AuditDbLogin`, а вход под root не из разрешённых источников отмечает как тревогу. Текст запросов сторож не сохраняет. Ценность: видно, кто и откуда входит в базу.

## Установка

- **Установщик: Keycloak, Völva и машина — из окна, MSI для Windows** (SPRINT_LORE_MODEL_DOCS_TIDY/MIG-04, #1619). Повод: новую установку приходилось настраивать вручную в Keycloak (область, роли, клиенты веба и MCP) и в Völva. Теперь окно установщика составляет план запросов к Keycloak, показывает его и выполняет только после подтверждения. Здесь же выпускается ключ встройки Völva, проверяется связь и заводится машина в LORE. Для Windows установщик поставляется офлайн-пакетом MSI. Node.js ставится, только если на машине его нет. Ценность: новую установку LORE можно поднять из одного окна, без ручной настройки в трёх системах.

## Мастер переноса

- **Решения переноса — в окне мастера, с записями за каждым значением** (SPRINT_LORE_MODEL_DOCS_TIDY/MIG-01, #1623, #1664, #1666, #1676). Повод: чтобы решить, к какому коду свести старый статус, надо было искать записи с ним отдельно, а задачи без спринта висели в воздухе. Теперь у значения статуса видно, какие записи его носят. Шаг «Задачи без спринта» предлагает спринт с основанием, а решает человек. Новый код статуса заводится прямо в окне с подписями на трёх языках (так появился REJECTED у ADR и решений). Ценность: перенос не стартует, пока по каждому значению нет решения, и видно, на что это решение влияет.
- **Ссылки решения становятся связями** (SPRINT_LORE_MODEL_DOCS_TIDY/MDL-08, #1659, #1674). Повод: в решении ссылки на ADR, спринт, PR и релиз лежали строкой, и по ним нельзя было перейти. Теперь при переносе они становятся связями. Неоднозначную ссылку (например, тег v1.0.0 у трёх проектов) человек разбирает в шаге «Ссылки решений». Ценность: из паспорта решения переходишь по ссылкам, а не ищешь их руками.

## Работа и планирование

- **«Зависит от» и треки спринтов** (SPRINT_LORE_MODEL_DOCS_TIDY/MDL-13, #1674). Повод: зависимость между задачами и спринтами была текстом в заметке, а параллельные линии работы внутри продукта не различались. Теперь «зависит от» — связь с видом зависимости, а у спринта есть трек. Ценность: план видит, что чего ждёт, и по каким линиям идёт работа.
- **Ответственный вопроса** (SPRINT_LORE_MEASURE_TRUTH/MT-MCP-TRUTH, #1628). Повод: у открытого вопроса не было того, кто должен ответить. Теперь это связь «кто отвечает». Ценность: видно, чьего ответа ждёт вопрос.
- **Вид продукта: ИТ или не ИТ** (SPRINT_LORE_WORK_ANY_KIND/WK-01, #1653). Повод: LORE ведёт не только программные продукты, и одного вида tech/service не хватало. Теперь у продукта набор видов с причиной выбора. Ценность: продукты без кода не выглядят как недоделанные ИТ-продукты.
- **Задача закрывается PR при мерже** (SPRINT_LORE_MODEL_DOCS_TIDY/MD-05, #1641). Повод: связь задачи с PR ставилась руками и часто терялась. Теперь мерж из LORE записывает данные PR и ставит связь «задача закрыта PR». Ценность: по задаче видно, каким кодом она сделана.

## Графики и аналитика

- **Две пачки графиков** (SPRINT_UXR_S13_KIT4/K4-CHARTS, #1636, #1637, #1632). Повод: из v1 в v2 не переехали графики, по которым видно течение работы. Теперь есть CFD, прогноз вехи, время цикла, WIP, возраст задач, блокировки, velocity по задачам, ритм релизов, действия агентов и отказы MCP; «Динамика» показывает полные ряды «Новостей», а графики спринтов вехи переехали из v1. Ценность: темп и узкие места видны в v2 без перехода в старый интерфейс.

## Супертеги и поиск

- **Супертеги: «#тег» с полями** (SPRINT_LORE_PRODUCT_BACKLOG/SUPERTAGS-SPIKE, #1658, #1661, #1674). Повод: метки были плоскими словами, у метки нельзя было завести свои поля. Теперь «#тег» набирается прямо в тексте, у тега есть поля, а экран «Теги» в меню показывает все записи с тегом. Ценность: свои разрезы по записям без новых типов в модели.
- **Поиск по графу в MCP** (SPRINT_SEIDRKIT_GRAPH_CANVAS/GC-05, #1647, #1638). Повод: агент искал связи пошаговыми вызовами. Теперь один вызов проходит граф от записи с фильтром по типам и направлению, а «похожие» находят по короткому названию и ранжированы. Ценность: агенту меньше вызовов на один вопрос.

## Админка и интерфейс

- **Экран «Модель» в админке** (SPRINT_LORE_MODEL_AS_CONFIG/MC-06, #1618). Повод: модель LORE правилась только файлом в репозитории. Теперь её можно править в админке: сначала пробный прогон без записи, с откатом. Ценность: настройку модели меняют без выпуска новой версии.
- **Меню и подписи связей из модели, пустые вкладки — под «Ещё»** (SPRINT_UXR_S14_KIT5, #1654, #1643). Повод: вкладки связей и их подписи жили в коде клиента, а пустые вкладки занимали место. Теперь они берутся из модели вместе с обратной подписью, пустые прячутся под «Ещё». Ценность: паспорт короче, а новые связи появляются в интерфейсе без правки клиента.

## MCP и наблюдаемость

- **MCP: вход парой client id и секрет** (SPRINT_LORE_AGENT_OBSERVABILITY/AO-MCP-HOSTED, #1620). Повод: подключать агента к MCP по адресу хоста было неудобно без готового токена. Теперь агент входит парой «клиент и секрет», а токен кэшируется. Ценность: подключение агента — это адрес, клиент и секрет.
- **Журнал медленных запросов к базе** (SPRINT_LORE_OWN_HOST/OH-SLOW-QUERY-LOG, #1640). Повод: когда экран тормозил, не было видно, какой запрос к базе медленный. Теперь медленные запросы пишутся в журнал. Ценность: причину тормозов видно сразу, а не по догадке.
- **Потолок расхода на попытку рутины гейта** (SPRINT_QG_REBUILD/QG-15, #1642). Повод: рутина гейта на модели могла потратить сколько угодно. Теперь у попытки есть потолок, а модель задаётся настройкой. Ценность: расход на проверки качества предсказуем.

## Установщик — дополнения

- **Справка в окне, архив исходников, Forgejo и локальная LLM** (SPRINT_LORE_MODEL_DOCS_TIDY/MIG-04, #1655, #1657, #1663, #1665). Повод: при установке приходилось держать рядом инструкцию, а Forgejo и forgejo-mcp ставились отдельно. Теперь у каждого шага окна есть справка «что нужно и как настроить». Forgejo и forgejo-mcp ставятся по выбору, образ forgejo-mcp лежит в пакете. Локальная LLM — по выбору, для гейтов качества. Исходники LORE лежат в пакете архивом для собственной сборки. Ценность: установку проходят по одному окну, без интернета и без ручной сборки образов.

## Технологии

- Версии движков и зависимостей LORE не менялись.
- Новые службы `lore-mcp` и `db-guard` собраны на той же базе, что и web-next: `node:26-alpine`.
- MSI-установщик для Windows содержит Node.js 26 LTS, если на машине нет Node.js версии 20 или новее.
