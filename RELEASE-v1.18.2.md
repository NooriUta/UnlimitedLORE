# LORE v1.18.2

Выпуск про установку у других. Пакет установки больше не содержит наших настроек: в нём нет наших адресов, областей Keycloak, имён машин и организаций, а исходник моста к git едет внутри пакета. Вместе со стеком ставится MCP, и агента можно подключить по адресу установки. У каждого агента своя учётка с ролью, и выпустить её можно из админки.

## Установка у других

- **В пакете нет наших настроек** (SPRINT_LORE_PRODUCT_BACKLOG/SELF-PROVISION-STANDALONE, #1726). Повод: адреса LORE и Keycloak впекались в образ при сборке, а в файлах пакета стояли наши домены, имена машин и организаций. Чужая установка с таким образом шла в наш Keycloak — тот же корень, из-за которого 15.11 вход прода ушёл на препрод. Теперь адрес и клиент входа читаются при запуске контейнера: сменил — перезапустил, пересобирать нечего. Адрес git-хоста берётся из настройки или из записи репозитория, а если его нет — приложение честно пишет «адрес не задан». Проверка в сборке ищет наши домены, области и имена машин в образе и в пакете. Ценность: установка у друга работает со своими адресами, а не молча ходит к нам.
- **Исходник моста к Forgejo едет в пакете** (SELF-PROVISION-STANDALONE, #1726). Повод: установщик собирал forgejo-mcp из нашего git, и без доступа к нему установка падала. Теперь исходник лежит внутри пакета с лицензией и контрольной суммой, сетевого обращения к нам при установке нет вовсе. Свой образ или свои исходники можно указать настройкой. Ценность: пакет ставится без связи с нашей инфраструктурой.
- **MCP ставится вместе со стеком** (SELF-PROVISION-STANDALONE, #1728). Повод: MCP был только у нас, а в пакете его не было — агента к чужой установке подключить было нечем. Теперь сервис MCP входит в установку, адрес `https://<хост>/mcp`, порт наружу не открыт. После установки проверяется, что MCP отвечает входом, а не ошибкой. В README появился раздел «Подключить агента к MCP» с примерами для Claude Code и OpenCode. Ценность: у чужой установки агенты работают сразу, а не после отдельной настройки.
- **Честный Keycloak: сначала спрашиваем, что уже есть** (#1725 в 1.18.1, #1728). Повод: установщик заводил область и клиентов, не спрашивая, есть ли они. Теперь окно спрашивает: своя область, LORE уже стоит, свои клиенты и секреты. Если всё своё, LORE не делает ни одного запроса на запись в чужой Keycloak — только проверяет, что по вашей паре выдаётся токен с нужной ролью. Уже заведённую область установщик доводит, ничего не удаляя и не перевыпуская секреты. Ценность: установщик не хозяйничает в чужом Keycloak.

## Учётки агентов

- **Вкладка «Учётки» у harness** (SPRINT_LORE_OWN_HOST/OH-MCP-HOSTED-SWITCH, #1731). Повод: учётки агентов жили в Keycloak, и чтобы узнать, какие есть и когда меняли секрет, приходилось открывать его консоль. Теперь в админке у каждого harness дерево «главная роль → младшие»: имя клиента, включена ли учётка, когда сменён секрет, перешёл ли агент на новый. Кнопки «Выпустить», «Сменить секрет», «Выключить». Выпуск роли выше главной недоступен, и сказано почему. Keycloak недоступен — так и написано, а не «учёток нет». Ценность: учётками агентов управляют из LORE, не заходя в Keycloak.
- **Секрет сразу попадает в хранилище** (OH-MCP-HOSTED-SWITCH, #1731). Повод: секрет показывался один раз, и человек переносил его в хранилище руками. Теперь при выпуске и смене LORE записывает его в Infisical ключом вида `LORE_MCP_CLIENT_SECRET_<РОЛЬ>`. Если запись не настроена, секрет по-прежнему показывается один раз и об этом сказано прямо. Ценность: секрет не теряется между окном браузера и хранилищем.
- **Подключение агента по имени ключа** (OH-MCP-HOSTED-SWITCH, #1731). Повод: клиент MCP умел брать секрет только из одной переменной, поэтому у разных ролей на одной машине он конфликтовал. Теперь имя переменной задаётся настройкой `LORE_MCP_SECRET_VAR`, и на машине могут жить учётки нескольких ролей. Ценность: подагент работает под своей ролью, а не под полной.

## Данные PR

- **Дотяжка данных PR из git-хоста** (SPRINT_LORE_MODEL_DOCS_TIDY/MD-05, #1730). Повод: у 547 из 1093 PR не было заголовка — в паспорте и в релизе стоял голый номер. Корень оказался не в переносе: PR одним номером заводили старый мерж через мост (исправлено в 1.18.0), ручная привязка PR к задаче и привязка PR к релизу без данных. Теперь обе привязки сразу подтягивают заголовок, адрес и состояние, а проверка в сборке не даёт заводить PR одним номером. Для уже накопленных есть операция дотяжки и шаг установки: идёт порциями, можно прогнать вхолостую, повтор ничего не меняет, чужие и недоступные репозитории пропускаются с причиной. Ценность: в списках и релизах у PR человеческий заголовок и ссылка.
