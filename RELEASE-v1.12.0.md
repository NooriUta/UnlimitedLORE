# v1.12.0 — прод-СУБД на ArcadeDB 26.10.2, скоуп проверен до последнего среза, CI на своём раннере

Минорный релиз: 29 PR (#651–#686), набранных с v1.11.2. Главное — три вещи: прод-база поднята на 26.10.2 через гейт, который умеет краснеть; скоуп по проекту доведён до состояния, когда включённым он не отдаёт 502 и не теряет многосвязное; оба CI ушли на выделенный раннер и перестали гонять тесты дважды.

## Прод-СУБД: ArcadeDB 26.10.2

- **Гейт подъёма** (#662, #669): два клона копии, одно открытие, законная убыль от прореживания MIDGARD отделена от находки. Классификатор гейта проверяет сам себя на каждом PR — гейт, который не умеет краснеть, не гейт.
- **Замеры вместо заметок** (#653, #659): картины 26.10.1 и 26.10.2 сняты пробами; поведение то же, ставить надо 26.10.2.
- **Подъём выполнен 20.10.2026**, Testcontainers в тестах переведены на 26.10.2 (#680). Сутки наблюдения за логом СУБД после подъёма — без находок на момент выпуска.
- Сверка схемы при старте краснеет, когда журнал миграций полон, а типа нет — тест на сам случай (#671). Ссылка на ранбук самоподъёма схемы в compose чинена (#674).

## Скоуп по проекту

- **V47** (#660): проект спеки, дока и ранбука выводится через ПРОДУКТ компонента.
- Тело документа обнуляется читателю без роли, строка остаётся (#658); обнуление включено, а вызывающий, которого нет в графе ролей, не считается отказом (#663). Спеки, доки и ранбуки под скоупом проверены, срез показывает цену включения (#652).
- **Под включённым скоупом `releases` и `decisions_of_adr` отдавали 502** (#675): условие скоупа вставлялось после ORDER BY. Сторож: у каждого PROJECT_SCOPED-среза условие стоит до ORDER BY/LIMIT/GROUP BY.
- **Решение под двумя ADR и задача в двух фазах** теперь видны в каждом родителе, а не в первом попавшемся (#677): фильтр по обходу — `CONTAINS`, а не `[0] =`.
- Ветки поиска идут по одной из-за изоляции отказа, а не из-за «потери `$score`» — замерена цена (#673).

## История и опросчики

- Открытая строка истории без `valid_from` становится видимой находкой — срез `history_hygiene` (#665).
- **Опросчики логинов KC и прогонов гейтов не запускались ни разу** (#676): ленивый бин без `@Startup` не создаётся, пока его не внедрят, — и прятал за собой отказ старта на пустом значении конфигурации. Теперь стартуют вместе с приложением; пустой список проектов — честное «не настроено» в логе.

## Агенты и MCP — меняет поведение

- **Права агентов расширены** (#686, решение владелицы D-2026-LORE-AGENT-MATRIX-WIDEN-PROFILES):
  - architect и pm могут заводить проекты;
  - product-analyst пишет задачи и статусы;
  - analyst и product-analyst — insight/metric;
  - analyst, product-analyst и marketer — rec;
  - в профилях developer и marketer явно запрещены `doc_del`/`spec_del`, у developer ещё `release_mv`.

  Сторож сверяет профили агентов с матрицей прав бэкенда: профиль не обещает того, чего бэкенд не пропустит.
- **`decision_new` терял `project`** (#685): ответ `ok:true`, а ребра к проекту нет. Сторож: каждый параметр схемы инструмента доходит до бэкенда. **Действует только после пересборки MCP**: MCP-сервер собирается из основного чекаута, а не со стенда.
- `forgejo_*` принимают путь репозитория вместо слага: ответ называет слаг, а не советует регистрировать дубль (#681). CI-статус по имени ветки со слэшем больше не отвечает UNKNOWN на зелёной ветке (#670).

## CI

- **Оба CI на выделенном раннере `lore-only`** (#668, #682); пробный `runner-probe.yml` снят (#683). Причина «фронтовый CI не работает с июля» найдена: метка раннера без привязки к образу.
- **Backend CI больше не гоняет весь набор тестов дважды** (#684): время сборки в `build-info.properties` делало тесты «устаревшими» при каждом вызове Gradle. Минус ~16 минут на джоб.
- Итог тестов печатается и на зелёном прогоне — «дельта зелёных» теперь берётся из лога CI (#678).
